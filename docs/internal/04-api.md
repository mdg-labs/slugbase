# SlugBase — API

The HTTP API is the whole product surface: the SPA, the Cloud operator console's product views, API-token scripts and any future browser extension use the same operations. Nothing the UI does is unavailable to an API-token caller with the same rights, and there are no undocumented endpoints (D12).

---

## 1. Contract and tooling

### 1.1 Code-first, generated, committed

| Job | Tool |
|---|---|
| Operation definitions (method, path, params, request and response bodies, errors, security, rate bucket, required role/entitlement) | `defineOperation()` in `@slugbase/contracts`, one file per tag under `packages/contracts/src/operations/`, with Zod 4 schemas. Omitting the policy fields is a compile error and a generator error that names the operation |
| Shared schemas (Bookmark, Folder, Problem, Page, …) | `@slugbase/contracts` — Zod schemas only; `zod` is its only runtime dependency, and it is importable by the server, the web app and the console |
| Route registration | A module contributes its routes in its `ModuleContribution` (doc 01 §7.1). Each route is `route(operation).handle(handler)` from `@slugbase/server`: the handler lives in `packages/server/src/routes/<domain>/`, is typed from the operation's request and response schemas and answers with one of the responses the operation declares. `createServer` refuses to start (a `CompositionError`) when a route's operation declares no valid policy (`missing_policy`), is absent from the OpenAPI document (`undocumented_operation`), differs from it in method, path or any policy extension (`policy_mismatch`) or is registered twice (`duplicate_route`). The route-level declarations of §5 (`acceptsMultipart`, `marketingOrigin`) are passed to `handle()` and are server-side only |
| OpenAPI document | Generated by `pnpm api:gen` into `packages/contracts/generated/openapi.json` (CE) and, in the Cloud build, a merged `openapi.cloud.json` that adds the Cloud modules' operations — **committed** |
| Typed client | `openapi-typescript` (types into `packages/contracts/generated/schema.d.ts`, committed) + `openapi-fetch` runtime wrapper in `packages/web/src/api/client.ts` |
| Lint | Spectral with a SlugBase ruleset: every operation has an `operationId`, a tag, `x-slugbase-auth`, `x-slugbase-rate`, at least one 4xx `application/problem+json` response, and no inline anonymous object schemas in responses |
| Breaking-change check | `oasdiff breaking` against the committed document at the latest release tag reachable from `main`; a breaking change in `/api/v1` fails CI (§2.2) |
| Exported-API reports | API Extractor writes `packages/*/etc/*.api.md` per package; a changed report is a contract change (doc 09 §3.3) |

**Which document a route is checked against.** By default `createServer` reads the committed `packages/contracts/generated/openapi.json`. A composition that adds operations (in Cloud, the modules of §10.11 and §10.12) passes the merged document as the `openApiDocument` option instead, and every route, its own and CE's, is then checked against that one.

**Drift check:** `pnpm contracts:check` regenerates `openapi.json`, `schema.d.ts` and the API Extractor reports and fails when the working tree differs. A route whose handler returns a body the response schema doesn't describe fails its contract test (§1.3) — the generated document can never describe an API the server doesn't serve.

### 1.2 The operation declaration carries the policy

Every operation declares, next to its schemas:

```ts
defineOperation({
  method: 'post', path: '/bookmarks', tag: 'bookmarks', operationId: 'createBookmark',
  auth: 'member',            // x-slugbase-auth: anonymous | account | member | admin | owner | instanceAdmin | machine
  entitlement: undefined,    // x-slugbase-entitlement, e.g. 'sharing.teams'
  rate: 'write',             // x-slugbase-rate: bucket from §7, or 'none' for probes and machine routes
  scope: 'write',            // x-slugbase-scope: API-token scope required, read | write; absent = not token-callable
  reauth: false,             // true = needs a fresh re-authentication (§4.4)
  request: { body: BookmarkCreate },   // strict: unknown fields are a 422
  responses: { 201: …, 400: problem, 403: problem, 409: problem, 422: problem },
})
```

The authorization middleware (doc 01 §4, step 9) reads these extensions — the policy is data the OpenAPI document publishes, not a decorator hidden in a handler. The generator and Spectral reject an operation without them, and the server refuses to start when a registered route's policy differs from the committed document. An operation that requires an account or member principal and declares no `scope` is not token-callable: a bearer request to it answers `403 forbidden`. On an `anonymous` or `machine` operation the token-callability and scope checks (steps 8 and 9) do not apply and the handler does not read the token's principal; the request is still a bearer request for the earlier steps, so it skips the cross-site check (step 5) like any bearer request (§5).

### 1.3 Contract tests

The integration suite (doc 08 §4) walks the generated document and, for every operation: calls it with a valid fixture and validates the response against its declared schema; calls it unauthenticated, with a too-low role, without the entitlement (Cloud entitlement source fixture) and with a read-only token on a write route, and asserts the declared 401/403 problem type; calls it from workspace B on workspace A's resource and asserts 404.

### 1.4 Reference docs

`GET /api/v1/openapi.json` serves the committed document byte for byte; `/api/docs` serves a Scalar reference UI from bundled assets (no CDN, CSP-compatible). Both can be disabled with `API_DOCS_ENABLED=false` (they then answer `404 not_found`; `/api/config` is unaffected); both are on by default in CE and Cloud (the API is public, its document is not a secret).

## 2. Conventions

### 2.1 Paths

| Prefix | Contents |
|---|---|
| `/api/v1/*` | The versioned JSON API |
| `/api/config` | Unversioned bootstrap config for the SPA (§9.1) |
| `/api/docs` | The API reference UI (§1.4) |
| `/go/<slug>` | Slug forwarding (§9.3) — not under `/api`, because it is typed into the address bar |
| `/opensearch.xml` | OpenSearch description so browsers can add SlugBase as a search engine (§9.4) |
| `/health`, `/ready`, `/version` | Process probes (§9.2) — unversioned, never behind auth |
| `/metrics` | Internal listener on its own port only, never on the public listener (which answers `404 not_found`) |
| everything else | The SPA, served from the web root the composition passes to the server (`webRoot`): content-hashed assets with `Cache-Control: public, max-age=31536000, immutable`, `index.html` with `no-cache`; `index.html` for any unknown `GET` with `Accept: text/html`; a `404 not_found` problem for an unknown path under `/api/` or `/go/` or without an HTML `Accept`. Only `GET` and `HEAD` are served |

Path segments are lower-case kebab nouns, plural for collections (`/bookmarks`, `/api-tokens`, `/audit-events`). The active workspace is **never** in the path (D11, doc 01 §5) — `/bookmarks` means "bookmarks in the active workspace". The few account-level resources live under `/me`; CE instance administration under `/instance`.

Actions that are not CRUD use a sub-resource noun (`POST /bookmarks/{id}/open`, `POST /invitations/accept`), never verbs in the collection path and never `?action=`.

### 2.2 Versioning

- `/api/v1` is the only version at launch. **Additive changes** (new operation, new optional request field, new response field, new enum value in a response marked `x-extensible-enum`) ship in `v1` without notice. Clients must ignore unknown response fields; the generated client does.
- **Breaking changes** (removed or renamed field, new required request field, narrowed type, changed status code semantics) go to a new `/api/v2` served **alongside** `v1` for at least six months, announced in the changelog and via a `Deprecation` + `Sunset` header on every `v1` response of the affected operations.
- The SPA always targets the newest version and ships with the server, so it never needs the overlap; the overlap is for API-token users and the browser extension (post-1.0).
- `oasdiff` enforces this mechanically (§1.1).

### 2.3 Representation

| Rule | Value |
|---|---|
| Media type | `application/json; charset=utf-8` for requests and responses; `application/problem+json` for errors; `multipart/form-data` only on the Netscape import upload |
| Field casing | `camelCase` in JSON; `snake_case` in the database; mapping lives in the repository layer |
| IDs | UUIDv7, lower-case hyphenated strings (`0192f1c4-…`); generated in the application, never by a database function (Q91); time-ordered, so they double as a creation-order tiebreak in keyset pagination. No sequential integers are ever exposed |
| Timestamps | RFC 3339 UTC with millisecond precision (`2026-10-08T09:51:26.123Z`); `timestamptz` in the database |
| Absent vs null | Optional fields are omitted when unset in requests; responses always include declared fields, `null` when empty. `PATCH` distinguishes "omitted" (unchanged) from `null` (clear) |
| Money (Cloud) | Integer minor units plus an ISO 4217 currency code — never floats, never formatted strings in the API |
| Enums | Lower-case snake strings (`owner`, `shared_with_me`, `past_due`) |
| Booleans | Never stringly typed; query-string booleans are `true`/`false` only |
| Unknown fields | Rejected with `422 validation_failed` (Zod `strict`) — a typo never silently does nothing |
| Locale | Problem `detail` is always English (doc 02 §15); the SPA renders localised text from `code`. The account locale and `Accept-Language` affect only emails; data is locale-independent |

### 2.4 HTTP semantics

- `GET` is safe and never changes state (the single exception, recording usage on `/go`, happens asynchronously and is not observable in the response).
- `POST` creates (201 + `Location` + body, except an operation that declares `idempotency`, which answers no header, §6.3) or performs an action (200/202/204).
- `PATCH` is JSON Merge Patch semantics on declared fields; `PUT` replaces a whole set (`PUT /teams/{id}/members`).
- `DELETE` answers `204`. Repeating it answers `204` only where the record keeps a state after the first call (a revoked API token, a revoked invitation) and only while the record is kept: a revoked API token's row stays until the retention purge removes it, 30 days after the revocation or the token's expiry, whichever is first (doc 05 §2.1, §6), and a repeat after that is `404 not_found`; a hard-deleted resource (bookmark, folder, tag, team, share) keeps no tombstone, so a repeat is `404 not_found`. A resource the caller never could see is `404` as well.
- **Not found vs forbidden:** a resource in another workspace, or one the caller has no read access to, is **404** — existence is never disclosed. **403** is returned only when the caller can see the resource but may not perform the action (a member deleting a bookmark shared with them).
- **Optimistic concurrency** on editable records: every bookmark, folder, team and workspace response carries `version` (an integer) and an `ETag`; `PATCH`/`PUT` accept `If-Match` and return `412 precondition_failed` on mismatch. The SPA sends it from the edit modal so two tabs don't silently overwrite each other. Optional for API-token callers. The `ETag` is the version as a quoted entity tag (`"3"`); `If-Match` takes one or a list of them, or `*`, which matches any version of a record that exists. The comparison is strong: a weak tag (`W/"3"`), a value that is not a version tag and an empty value match no version, so a header the server cannot read refuses the change with `412` instead of passing it. The version is compared under the record's row lock, so of two changes made against one version the second is refused. A change that leaves the record as it is (a `PATCH` naming the value it already has) answers `200` with the unchanged `ETag` and writes no audit event.

## 3. Errors

### 3.1 Shape

Every error is an RFC 9457 problem document:

```json
{
  "type": "https://slugbase.app/problems/slug_taken",
  "title": "Slug already in use",
  "status": 409,
  "code": "slug_taken",
  "detail": "You already use the slug \"mail\" in this workspace.",
  "requestId": "01J9…",
  "errors": [ { "path": "slug", "code": "slug_taken" } ]
}
```

- `code` is the stable machine identifier; `type` is its URL form; `title` is static per code (English); `detail` is English and may contain user-supplied values (escaped by the client). The SPA renders localised text from `code`.
- `errors[]` appears on `validation_failed` and on per-field domain errors, with JSON-pointer-ish `path`s matching the request body.
- `requestId` echoes the `X-Request-Id` response header for support.
- **Never** a stack trace, SQL, an internal identifier the caller couldn't already see, or a hint that distinguishes "no such account" from "wrong password".

### 3.2 Code catalog

| Status | `code` | When |
|---|---|---|
| 400 | `bad_request` | Malformed JSON, or a pagination cursor that does not match the request (§6.1) |
| 401 | `unauthenticated` | No valid session or token; also the one generic answer to sign-in with an unknown email, a wrong password or a disabled account, and to a revoked, expired or disabled-account token |
| 401 | `mfa_required` | Session exists at `partial` level; complete `POST /auth/mfa/verify` |
| 401 | `reauth_required` | Sensitive operation needs a fresh re-authentication (§4.4) |
| 403 | `forbidden` | Authenticated, can see the resource, may not do this; also a bearer request to an account or member operation that is not token-callable, an instance-admin operation without MFA enrolled, and `POST /setup` with a missing or wrong setup token |
| 403 | `registration_refused` | A deployment's registration policy refused this sign-up (doc 01 §13); the response is the same for every refusal reason |
| 403 | `cross_site_request` | Origin / Fetch-Metadata / content-type check failed (§5) |
| 403 | `token_scope` | API token has `read` scope on a write operation |
| 403 | `entitlement_required` | Plan doesn't include the feature; body carries `entitlement` and, on Cloud, `upgradeAvailable: true` |
| 403 | `email_unverified` | Verification is required and the account is unverified (sign-in with a correct password creates no session; Cloud actions that need a verified email) |
| 403 | `registration_closed` | Public registration is off |
| 403 | `setup_completed` | `POST /setup` after setup, or with setup turned off |
| 404 | `not_found` | Unknown, or not visible to the caller (§2.4); also any operation that needs a workspace (`mem`, `adm`, `own`) from a principal that has none |
| 404 | `slug_not_found` | `/go` and `POST /go/choose`: no accessible forwarding bookmark |
| 409 | `slug_taken` | The caller already uses this slug in the workspace |
| 409 | `name_taken` | Folder, tag, team or API-token name already exists for that owner/workspace |
| 409 | `email_taken` | Invitation accept with registration fields for an email that already has an account — **only** where the flow is not enumeration-sensitive: the holder of a live invitation token already learns it from `POST /invitations/inspect`, for the invited address alone; registration and email change respond generically instead (doc 02 §2) |
| 409 | `already_member` | Invitation for, or accept by, an existing member; an instance admin adding themselves to a workspace they already belong to |
| 409 | `last_owner` | Removing, demoting or the departure of the last owner; deleting an account that is the only owner of a workspace with other members (the body lists the blocking workspaces by id and name) |
| 409 | `workspace_has_owner` | An instance admin asks for a new owner invitation for a workspace that has an owner already |
| 409 | `idempotency_conflict` | Same `Idempotency-Key` with a different request body (§6.3) |
| 409 | `billing_active` | A deployment extension refuses deleting a workspace or account (Cloud: it owns an active paid subscription); CE composes no such guard |
| 410 | `token_expired` | Verification, reset, email-change or invitation token unknown, expired, used or revoked — one identical answer |
| 412 | `precondition_failed` | `If-Match` mismatch |
| 413 | `payload_too_large` | Body over the route limit (default 64 KiB; the import routes allow 5 MiB) |
| 415 | `unsupported_media_type` | A bearer request whose mutation is not JSON, whatever the operation's auth policy (cookie requests and requests with no `Authorization` header get `cross_site_request`, §5) |
| 422 | `validation_failed` | Schema validation; `errors[]` lists fields |
| 422 | `bookmark_limit_reached` | Create would exceed the bookmark cap; carries `limit` and `used`. Import never returns it: it adds up to the limit and reports the rest as skipped |
| 422 | `seat_limit_reached` | Invitation accept with no free seat (Cloud) |
| 422 | `workspace_limit_reached` | Creating a workspace beyond the account entitlement; carries `limit`, `used` and `upgradeAvailable` |
| 422 | `weak_password` | Fails length/breach policy (Q15); `errors[]` codes `too_short`, `too_long`, `breached` |
| 422 | `invalid_code` | Wrong or replayed TOTP or backup code (counts against the MFA bucket) |
| 422 | `url_not_allowed` | URL scheme not `http`/`https`, or host fails egress policy for a fetch |
| 429 | `rate_limited` | With `Retry-After` and `RateLimit-*` headers (§7) |
| 502 | `upstream_failed` | Metadata/AI/billing provider failed; the operation is retryable |
| 503 | `unavailable` | Not ready (migrations pending, DB unreachable), the rate-limit store failed, or the port is unconfigured (`mail_unavailable`, `ai_unavailable` and, for the CE billing adapter, `billing_unavailable` as `code`) |
| 500 | `internal` | Everything else; logged with the request ID, reported through the error port |

Field codes inside `errors[]` of a `422 validation_failed` or a `403 forbidden`:

| Field code | Operation | Meaning |
|---|---|---|
| `api_token_limit_reached` | `POST /me/api-tokens` (`422 validation_failed`, on `name`) | The account already has 10 tokens that are neither revoked nor expired |
| `invitation_email_mismatch` | `POST /invitations/accept` | The signed-in account's verified email is not the invited address (`403 forbidden`) |
| `invalid_password` | `POST /me/reauth` (`401 reauth_required`), `POST /me/password` on `currentPassword` (`422 validation_failed`) | The password is wrong, or the account has none; one answer for both, so the response does not tell them apart |
| `last_sign_in_method` | `DELETE /me/identities/{id}` | Would leave the account with no way to sign in |
| `last_instance_admin` | `DELETE /me` (`422 validation_failed`, on `email`), `PATCH` / `DELETE /instance/accounts/{id}` (on the field that was refused, `id` for the deletion) | Would leave the instance without an enabled admin; `DELETE /me` refuses the last enabled instance admin the way the instance routes do, and a disabled admin does not count as another one |

New codes are additive (§2.2); a client must treat an unknown `code` by its `status`.

## 4. Authentication

### 4.1 Principals

| Principal | Credential | Carries | Cross-site check (§5) | MFA |
|---|---|---|---|---|
| **Session** | `__Host-slugbase_session` cookie (`slugbase_session` without `Secure` when `APP_ORIGIN` is http) | account, active workspace, auth level (`partial` → `full`), re-auth timestamp | Required on unsafe methods | Enforced at login |
| **API token** | `Authorization: Bearer slb_<43 base64url characters>` (32 random bytes) | account, **bound workspace**, scope (`read` / `read-write`) | Not applied (no ambient credential) | Not applicable (an already-trusted credential, D10) |
| **Machine** | Route-specific: a module's inbound event endpoint (in Cloud, the billing service's events; no session; sender signature verified, idempotent), internal metrics port | nothing | Not applied | — |
| **Anonymous** | none | — | Required on unsafe methods (login, register, setup, password reset, invitation accept) | — |

When an `Authorization` header is present, cookies are **ignored** for that request — a request is either a token request or a browser request, never both. A bearer header that no resolver accepts is `401 unauthenticated` without falling back to a cookie. An operation that declares an `audience` (`machine`, `marketing-form`) resolves no principal from the `Authorization` header or the cookies, so that `401` applies to operations without an `audience`.

### 4.2 API tokens and workspaces

A token is created by a member for one workspace they belong to (default: the active one) and **bound** to it: every request made with it acts in that workspace, with the account's current role there, regardless of the account's session. A token cannot switch workspaces and is accepted only by account and member operations that declare a scope (the † marker in §10) — token management, sessions, MFA, email, password, account deletion and `/instance/*` declare none, so a token gets `403 forbidden` there. On an `anonymous` or `machine` operation (for example `GET /api/config` or `POST /auth/login`) the token-callability and scope checks (steps 8 and 9) do not apply and the handler does not read the token's principal; the request is still a bearer request for the earlier steps, so it skips the cross-site check (step 5) like any bearer request. A member who loses membership loses every token bound to that workspace (deleted in the same transaction as the membership; the token's next request is `401`). Tokens of a disabled account are inert (`401`).

Multi-workspace automation uses one token per workspace. An `X-Slugbase-Workspace` header override is **not** offered at v1 (Q40).

### 4.3 Session levels

- `partial`: password verified, TOTP pending. Only `POST /auth/mfa/verify`, `POST /auth/logout` and `GET /api/config` accept it; every other operation that needs a session returns `401 mfa_required` (an `anon` operation never looks at the session). Expires after 5 minutes, and a request does not extend it; five failed codes revoke it. `POST /auth/login` makes a `partial` session only for an account whose MFA is on, and never a `full` one.
- `full`: signed in. The session token is **rotated** on sign-in, on the `partial → full` transition and on every privilege change (role change of the account itself in the active workspace, instance-admin flag change, password change, MFA enabled or disabled).

### 4.4 Re-authentication ("sudo mode")

Destructive or credential-changing operations require `reauthAt` within the last 10 minutes on the session (the `Re` column of §10): change password, change email, start MFA enrolment, disable MFA, regenerate backup codes, create an API token, unlink a sign-in method, start linking one (`GET /auth/oidc/{provider}/start?intent=link`), delete the account, delete a workspace, transfer ownership, and the instance-admin operations marked ✓. Without it they return `401 reauth_required`; the SPA prompts for the password or a TOTP code via `POST /me/reauth` (accounts without a password re-authenticate through the provider: `GET /auth/oidc/{provider}/start?intent=reauth`, whose callback sets `reauthAt` for the session of the browser when the provider asserts an identity the account holds; an account whose second factor is on may give a code instead) and retries. Starting a link is the one gated action that is a browser redirect rather than a JSON call: its start answers `401 reauth_required` as a problem document (nothing is stored), so the page can send the member through re-authentication first, and its callback checks the same window again, because up to ten minutes pass between the two; a lapse ends on `/login?error=oidc_failed` and links nothing. The `reauth` and `login` intents are not gated. The freshness check tolerates a difference of up to 5 seconds between the database clock that stamps `reauthAt` and the application clock; the 10-minute end of the window is exact.

### 4.5 Sign-in flows (shape only — behaviour in doc 02 §2)

| Flow | Calls |
|---|---|
| Password | `POST /auth/login` → `200 { next: "done" }` or `{ next: "mfa" }` (partial session) → `POST /auth/mfa/verify`. Unknown email, wrong password and disabled account are one `401`; an unverified account gets `403 email_unverified` when verification is required |
| OIDC | `GET /auth/oidc/{provider}/start?returnTo=&intent=` → `302` to IdP (state, nonce, PKCE stored server-side, doc 05 §2.1) → `GET /auth/oidc/{provider}/callback` → `302` to `returnTo` (same-origin paths only; anything else is `/`). The handshake is bound to the browser by a short-lived pre-auth cookie (`__Host-slugbase_oidc` over https, `slugbase_oidc` over http; 10 minutes; cleared when the callback ends); the callback address to register with the provider is `<APP_ORIGIN>/api/v1/auth/oidc/<slug>/callback`. A sign-in with a linked identity creates a `full` session without a SlugBase code. `intent` is `login` (default), `link` (add the identity to the signed-in account), `reauth` (satisfy `POST /me/reauth` for a passwordless account) or `invite` (accept an invitation through the provider; it takes `invitation=<token>`, required for it and refused with any other intent, and reads no `returnTo`: the browser ends on `/`, where the workspace it joined is the active one). `link` and `reauth` are started only by a complete session (not a pending-MFA session, not an API token), and `link` only by one that re-authenticated within the last 10 minutes (§4.4: otherwise `401 reauth_required`; `reauth` is how a session gets there) in a request that a browser reports as coming from the application itself with `Sec-Fetch-Site` (`same-origin`, or `none` for the address bar; a request from another site, a sibling subdomain included, or without the header is refused, so a browser that sends none cannot start one; `login` is not gated, and on that browser an account with a password re-authenticates with it, one with a second factor and no password uses a code, and one with neither cannot re-authenticate): the handshake stores the starting account in `oidc_login_states.link_account_id` (doc 05 §2.1), and `reauth` asks the provider for the credentials again and for no older authentication (`prompt=login` with `max_age=0`). The callback of `link` or `reauth` is accepted only in a browser whose current session is a complete session of that same account, besides the pre-auth cookie. `link` adds the identity to that account only, and only while the session is still within the re-authentication window, keeps the account's sessions as they are and refuses an identity another account holds; `reauth` sets `reauthAt` on the browser's session only when the provider asserts an identity that account holds and its ID token was authenticated no earlier than the second the handshake began in, less the 60 seconds of clock skew allowed between the provider and the server for `exp`, `iat` and `nbf` (`auth_time` is the provider's clock and the start is the server's; a provider that omits `auth_time` is accepted on `prompt=login` alone), and the browser goes on to `returnTo` in both. An ID token signed with a key id the cached key set of the provider does not hold makes the server fetch that key set once more, at most once a minute for a provider, before the token is refused, so a key rotation at the provider does not fail sign-ins until the cache expires. The `invite` intent needs no session (a session cookie the browser carries is replaced by the one the acceptance makes), is started only in a request that a browser reports as coming from the application itself, by the same `Sec-Fetch-Site` rule as `link` and `reauth` (a refused start stores no handshake record and takes nothing from `token_redeem`; a browser that sends no header accepts by signing in or registering on the invitation page instead, as `POST /invitations/accept` is held to §5), and counts as a redemption against `token_redeem` (§7): per client address, and per account when the browser holds a complete session. The server hashes the token at once; the handshake record keeps only that hash (`oidc_login_states.invitation_token_hash`, doc 05 §2.1), used once with the state (the callback deletes the record when it consumes it) and kept no longer than the state's 10 minutes, and nothing of the token goes into the authorization address, a cookie or a path to come back to; a text that is not an invitation token ends on `/login?error=oidc_failed` and stores nothing. The callback accepts the invitation only when the identity port has verified the ID token and the provider asserted `email_verified=true` for exactly the invited address (compared the way accounts compare addresses; an unverified, absent or different address accepts nothing, links nothing and creates nothing). Which account accepts is decided in one database transaction (`sys_invitation_accept_with_identity`, doc 05 §3.3): the account the identity is linked to, else the enabled account that holds the invited address verified, to which the identity is linked, else a new account for the invited address, verified and without a password, with the identity linked, whatever `OIDC_<SLUG>_AUTO_CREATE` and `OIDC_<SLUG>_ALLOWED_DOMAINS` say, because the invitation authorises it (Q31); creating one first asks the registration policy with the path `invitation` and is refused with the same generic failure when it says no. The checks of the signed-in acceptance apply (the account's address verified and equal to the invited one, no membership yet, a seat left, a pending invitation that has not expired), and the link or the account, the membership with exactly the invited role, the accepted invitation, the `member.joined` audit event and domain event (and `account.created` with the path `invitation` for a new account) and a `full` session that acts in the invitation's workspace are one transaction: a refusal at any step writes nothing and leaves the invitation pending. The provider is trusted for the second factor, as for any sign-in through it. A callback whose sealed PKCE verifier cannot be opened (its secret-box key was removed meanwhile) ends like any other failure. Any failure ends on `/login?error=oidc_failed`, one generic code that does not say which step refused or whether an account exists |
| Registration (if enabled) | `POST /auth/register` → generic `202` → email link `/verify-email#token=…` (fragment, so the token never reaches server logs or `Referer`) → SPA calls `POST /auth/verify-email` with the token and the password the owner chooses, which verifies the account, creates its personal workspace and signs it in |
| Password reset | `POST /auth/password/forgot` → generic `202` → link `/reset-password#token=…` → `POST /auth/password/reset` (revokes every session of the account and creates a fresh one, `partial` when the account has MFA, so the mailbox alone does not replace the second factor) |

## 5. Cross-site request rules

Applied by middleware before routing (doc 01 §4, step 5) to every `POST`, `PUT`, `PATCH` and `DELETE` that does **not** carry an `Authorization: Bearer` header (whatever the operation's auth policy, an `anonymous` one included) and is not a `machine` or `marketing-form` route:

1. `Origin` must be present and equal `APP_ORIGIN` exactly (scheme, host, port). A missing `Origin` on an unsafe method is rejected.
2. `Sec-Fetch-Site`, when present, must be `same-origin`.
3. `Content-Type` must be `application/json`, with or without parameters such as `charset`. This holds for **every** mutation, including a `DELETE` without a body, so the SPA client sends `Content-Type: application/json` on all of them. The one exception is a route that declares `acceptsMultipart: true`, which also accepts `multipart/form-data`; only the Netscape import upload does. This makes every mutation a non-simple request a cross-site HTML form cannot produce.

Failure is `403 cross_site_request`, logged at `warn` with the offending origin. This step owns the content-type rule for every request without a bearer token, cookie-authenticated or anonymous; bearer requests skip it, and for them a non-JSON mutation is `415 unsupported_media_type` (body-limit stage). There is **no exemption list** (Q5): login, logout, registration, setup, MFA and reset are protected exactly like everything else, because they are all same-origin calls from the SPA.

A request that carries an `Authorization` header, and a request to a route with an `audience`, has its cookies dropped at this step, so no later stage or handler acts on the browser's session.

### 5.1 Route declarations

The audience of an operation is part of its contract (`x-slugbase-audience`). The two declarations below that only the server can enforce are options of `route(operation).handle(handler, options)` (§1.1); they are not in the contract or the OpenAPI document.

| Declaration | Where | Meaning |
|---|---|---|
| `acceptsMultipart: true` | `handle()` option | The route reads a `multipart/form-data` body itself, so rule 3 also accepts that media type, and the validation stage does not parse the body against the operation's body schema |
| `marketingOrigin` | `handle()` option | The one origin a `marketing-form` route accepts, as scheme, host and optional port (`https://example.org`, no path) |

A `machine` route skips rules 1 to 3 and has its cookies dropped; the handler verifies the sender's signature (doc 01 §4).

A `marketing-form` route is checked instead by:

1. `Origin` must be present and equal the route's `marketingOrigin` exactly; otherwise `403 cross_site_request`. `APP_ORIGIN` is not accepted on such a route.
2. `Content-Type` must be `application/json`; otherwise `403 cross_site_request`. A `marketing-form` route cannot accept multipart.
3. The visitor's bot-protection solution travels in the `X-Challenge-Solution` request header and is checked through the challenge port. A missing or unsolved challenge is `403 forbidden`, not `cross_site_request`.

`createServer` throws a `CompositionError` with code `invalid_route` when a `marketing-form` route has no valid `marketingOrigin`, when it is not a `POST`, `PUT`, `PATCH` or `DELETE` operation, or when any other route sets `marketingOrigin`. A declaration the server cannot enforce is a startup failure, never a silent exemption.

No CORS headers are ever emitted on `/api/*`; preflights get `403 cross_site_request`. Forms on a separate marketing origin therefore do **not** call the app origin from the browser: the marketing site proxies them same-origin to the server over the internal network, and their routes declare `audience: 'marketing-form'` with the marketing site's origin as `marketingOrigin` (Q41; doc 01 §4 step 5).

`GET /go/<slug>` is a safe method and relies on `SameSite=Lax` (sent on top-level navigation from the address bar, not on cross-site subresource requests) plus the fact that it has no side effects beyond the asynchronous usage counter.

## 6. Collections

### 6.1 Keyset pagination

Every list operation is cursor-paginated; there is no offset pagination anywhere.

```
GET /api/v1/bookmarks?sort=recent&limit=48&cursor=eyJr…
→ { "items": [ … ], "nextCursor": "eyJr…" | null, "total": 1234 | null }
```

- `limit`: default per resource (bookmarks 48, others 50), maximum 100.
- `cursor`: opaque, base64url JSON of the last item's sort key and `id`, **HMAC-signed** with a purpose-bound subkey derived from the server secret (no extra key to configure) so a client can't forge positions or smuggle filter changes; a cursor is valid only with the filter, search text and sort it was issued for (mismatch → `400 bad_request`).
- `total`: returned for bookmarks, folders and tags lists (the UI shows counts), computed by a `count(*)` over the same filter — capped: above 10 000 it returns `null` and `totalAtLeast: 10000` (Q42).
- The UI's page selector (24/48/96) maps to `limit`; "page N of M" is replaced by "load more" and a count, because keyset pagination has no random page access. The design prototype's pager is adapted accordingly (doc 03).

### 6.2 Filtering and sorting

Filters are query parameters named after fields, validated by Zod; repeated keys for multi-value (`?tag=a&tag=b` — AND semantics for tags, OR is not offered). Sorting is `sort=<key>` from a per-resource allowlist; direction is part of the key (`recent`, `oldest`, `title_asc`, `title_desc`, `most_used`, `recently_opened`). Free-text is always `q`.

"Select all across pages" uses `GET /bookmarks/ids` with the same filters, returning up to 5 000 IDs (the select-all cap, a fixed value, `BOOKMARK_SELECT_ALL_CAP` in `@slugbase/contracts`, doc 02 §16); bulk operations accept either an ID list (≤ 1 000) or the same filter object, and a filter matching more than the cap is `422 validation_failed`, so the server never needs the client to round-trip thousands of IDs (§10.6).

### 6.3 Idempotency keys

Operations that create billable or externally visible effects accept `Idempotency-Key` (a client-generated UUID): **required** on the billable mutations a module declares (in Cloud: checkout, seat changes and cancellation, Cloud doc 06); **accepted** on `POST /invitations`, `POST /import/*`, `POST /bookmarks`. The server stores `(account, key, operation, request hash) → response` for 24 hours (doc 05 §2.10); a replay returns the stored response with `Idempotency-Replayed: true`; the same key with a different body is `409 idempotency_conflict`; a concurrent duplicate waits on the first via a row lock rather than running twice. The mechanism is a route-level option an operation declares; keys are scoped to the account, so the same UUID used by two accounts never collides.

The option is `idempotency: true` in the operation's declaration in `packages/contracts`; it is published as the optional `Idempotency-Key` header parameter and `x-slugbase-idempotency` in `openapi.json`, and `createServer` refuses a route whose declaration differs from the document's. `POST /invitations` and `POST /bookmarks` declare it so far; the `required` form of the billable mutations is added with the first operation that needs it. A request without the header runs as usual; a header that is not a single UUID is `400 bad_request`. The stage (`idempotency`, step 9a of doc 01 §4) runs after authorization, so a replay is judged by the same policy as the first request, and it opens the transaction the handler runs in: the key, the handler's writes (the audit event and the queued jobs included) and the stored response commit together, and a request that ends in a problem or in a status other than `2xx` rolls back with its key, so the retry runs. A replay answers the stored status and JSON body with `Idempotency-Replayed: true`; headers of the first response are not restored, so an operation that declares idempotency documents none on its success responses. The request hash covers the operation, the workspace the request acts in and the validated path parameters, query and body, so the same key and body in another workspace is also `409 idempotency_conflict`. A concurrent duplicate waits on the unique index of the key for at most five seconds and then answers `503 unavailable`; the client retries with the same key. A key past its 24 hours is treated as unused and replaced; `sys_retention_purge` deletes it later.

## 8. Response headers

On every API response: `X-Request-Id`, `Cache-Control: no-store`, `Content-Type`, the security headers of doc 01 §4 step 2. An operation may declare its own cache policy in the contract; only `GET /api/config` (`public, max-age=60`, §9.1) and `GET /favicons/{host}` (`private`, long-lived) do. On collections: none beyond the body (no `Link` headers). On rate-limited routes: `RateLimit-*`. On editable records: `ETag`. On deprecated operations: `Deprecation`, `Sunset`, `Link: rel="deprecation"`.

## 9. Public and process endpoints

### 9.1 `GET /api/config`

Unauthenticated, cacheable for 60 s (`Cache-Control: public, max-age=60`; the per-operation override of §8), the only thing the SPA needs before sign-in:

```json
{
  "apiVersion": "v1",
  "origin": "https://cloud.slugbase.app",
  "product": { "name": "SlugBase", "version": "1.4.2" },
  "signIn": { "password": true, "registration": true, "oidc": [ { "slug": "google", "name": "Google" } ] },
  "setupRequired": false,
  "setupTokenRequired": false,
  "instance": { "displayName": "SlugBase", "signInNotice": null },
  "locales": ["en", "de"], "defaultLocale": "en",
  "features": { "mail": true, "ai": true, "billing": true, "analyticsConsentRequired": true },
  "legal": { "imprintUrl": "…", "privacyUrl": "…", "termsUrl": "…" }
}
```

The document starts small and grows additively (§2.2): `apiVersion`, `origin`, `product`, `locales`, `defaultLocale`, `docsBaseUrl` (the configured documentation base URL, default `https://slugbase.app/docs`, from `DOCS_BASE_URL`; the help links of doc 03 are built on it) and `features.mail` / `features.ai` exist from the first server; `setupRequired` is the answer of `GET /setup/status` (the deployment has setup on and the instance has no account and never completed setup) and is present on every response of the Community server; `setupTokenRequired` is the other half of that answer, `true` only while setup is pending and the deployment has `SETUP_TOKEN_REQUIRED` on (so the setup wizard asks for the token only then), `false` otherwise, and a flag only: never the token or its hash; `signIn`, `instance`, `legal`, `features.billing` and `features.analyticsConsentRequired` are added by the features that can populate them (doc 01 §11). `signIn.oidc` lists only enabled providers that answered discovery, never a secret or a provider URL. `signIn.registration` is true when `POST /auth/register` takes registrations now: public registration is on (`PUBLIC_REGISTRATION`, with the default the composition root supplies) and, when verification is required (`EMAIL_VERIFICATION_REQUIRED`), a mail adapter is configured. `instance.displayName` and `instance.signInNotice` are the instance settings of §10.10: the display name is the stored one, else the product name, and the notice is `null` while there is none; `instance` is present on every response of this server; the notice is plain text and the sign-in page renders it as text only, never as HTML (doc 10 T14). Like the rest of the document they are cached for 60 seconds.

`features` reports **whether a port is configured**, never entitlements (those need a workspace — `GET /entitlements`). `billing: true` only means a non-no-op billing adapter is composed; the SPA uses it to decide whether to load the Cloud extension routes' data, not to branch product behaviour (D4).

| Endpoint | Returns | Notes |
|---|---|---|

| `GET /ready` | `200` / `503` with `{ database, migrations: { expected, applied } }` | DB reachable and migrations at the build's level; a database ahead of the build logs a warning and stays ready. ### 9.3 `GET /go/<slug>`

Not part of `/api/v1`, but specified here because it is the product's main entry point. It is a browser navigation: a bearer token answers `401`, and the `go` bucket applies.

| Situation | Response |
|---|---|
| Not signed in | `302 /login?returnTo=/go/<slug>` (the sign-in pages honour `returnTo` only for a same-origin `/go/<valid slug>` path) |
| Partial session | `302 /login/mfa?returnTo=…` |
| Slug grammar invalid | SPA not-found page (`404`, HTML) |
| No accessible forwarding bookmark | SPA "slug not found" page (`404`, HTML) offering "create a bookmark with this slug" and, when the slug resolves in another workspace of the member, "switch and continue" (`otherWorkspaces`, §10.8) |
| Exactly one match, or a remembered preference | `302 <destination>` with `Referrer-Policy: no-referrer`, `Cache-Control: no-store`; usage recorded asynchronously |
| Several matches, no preference | SPA disambiguation page (`200`, HTML) at the same URL; the SPA calls `POST /api/v1/go/resolve` |
| Extra path or query after the slug (`/go/jira/PROJ-12`) | `404` slug-not-found page; path appending is post-v1 (Q43) |

The HTML pages carry `Cache-Control: no-store` and `Referrer-Policy: no-referrer` as well. Only `http:` and `https:` destinations are ever redirected to (enforced on write and re-checked on read); `javascript:`, `data:` and anything else is impossible by construction.

### 9.4 `GET /opensearch.xml`

Unauthenticated, `Content-Type: application/opensearchdescription+xml`, built only from `APP_ORIGIN` and the product name (never from the request's `Host` or `X-Forwarded-Host`) and no user data. Its search URL is `<origin>/go/{searchTerms}`; the SPA shell links it with `<link rel="search">` so browsers can offer SlugBase as a search engine in one click.

A token that is unknown, malformed, used, revoked, replaced or expired, or of a workspace being deleted, is one answer, `410 token_expired`, in both forms; the seat limit is the workspace's `seats.max` as the entitlement engine reads it (unlimited on the Community Edition), replaced by the answer of the registered seat-check hooks (the lowest limit when several answer), and the database counts the members under the workspace's lock and refuses with `422 seat_limit_reached` when their count already equals it, so two people accepting the last free seat add one member; a seat-check hook that throws, answers outside its contract or does not answer in time makes the acceptance `503 unavailable` and writes nothing, and sending, resending and listing invitations never count a seat. Every refusal writes nothing and leaves the invitation pending. A token is accepted at most once however many requests carry it, so parallel requests create one account and one membership. `POST /bookmarks` is implemented as far as `{ url, title, description?, pinned?, folderIds?, tagIds?, tagNames? }`: it answers `201` with the bookmark (its `id` and `version` in the body), and no `Location` or `ETag`, since it declares `idempotency` (§6.3) and a replay restores only the status and the body; a read of the bookmark carries the `ETag`. A URL that is not `http` or `https` is `422 url_not_allowed`, and an empty, over-long (2 048 characters) or malformed one is `422 validation_failed` on `url`. It declares no entitlement to stage 9: the handler reads `bookmarks.max` and the database takes the place under the workspace's lock (doc 01 §7.5, doc 05 §3.3), so a ceiling of zero answers `422 bookmark_limit_reached` with `limit` and `used`, and not `403 entitlement_required`. `GET /bookmarks/{id}` answers the caller's own bookmark; another member's bookmark of the workspace, a bookmark of another workspace and a plan-archived one are `404 not_found`.

Every bookmark body carries `folders`, the caller's folders it is filed in as `{ id, name, icon, color }`, in the order of their names (an empty list for a bookmark in none). `folderIds` (at most 100 identifiers, one named twice counting once) files a new bookmark in those folders in the transaction that creates it, and on `PATCH` replaces the folders the bookmark is in (`[]` takes it out of all of them; left out, they stay). A folder that is another member's, another workspace's or unknown is `404 not_found` and nothing is created or changed. Filing moves no version: a `PATCH` of `folderIds` alone answers `200` with the unchanged `ETag`. `GET /bookmarks` takes `folderId` and lists the caller's bookmarks filed in that folder, counted and paged like any list (the cursor is bound to the folder); a folder that is not the caller's, whoever's it is, or does not exist lists an empty page and is not an error. `GET /bookmarks/ids` does not take `folderId`.

Every bookmark body also carries `tags`, the caller's own tags on it as `{ id, name }`, in the order of their names (an empty list for a bookmark with none); another member's tags are never in it. `tagIds` and `tagNames` (each at most 100, a name 1–40 characters after the whitespace around it is removed; together they name the union) put tags on a new bookmark in the transaction that creates it, and on `PATCH` replace the tags the bookmark has by that union (`[]` or `tagIds: []` takes all of them off; both left out, the tags stay). A tag named by identifier that is another member's, another workspace's or unknown is `404 not_found` and nothing is created or changed; a name the caller has no tag of, whatever the case it is written in, creates the tag in the same transaction, and nothing is created when the request is refused for any reason. Only the owner tags a bookmark, and only with their own tags (doc 02 §8.2, Q22, which supersedes the member-may-tag-a-shared-bookmark remark of doc 05 §2.4). Tagging moves no version: a `PATCH` of `tagIds` or `tagNames` alone answers `200` with the unchanged `ETag`, and a patch that names the tags the bookmark has writes nothing. `GET /bookmarks` takes `tag`, repeated (`?tag=<id>&tag=<id>`, at most 10): it lists the caller's bookmarks that carry every one of the given tags (AND; OR is not offered), counted and paged like any list (the cursor is bound to the set of tags). Tags are addressed by identifier, so a rename breaks no link; a tag that is not the caller's, whoever's it is, or does not exist lists an empty page and is not an error. `GET /bookmarks/ids` does not take `tag`.

A tag is private to the member who made it (doc 02 §7.2, doc 05 §2.4): another member's tag, a tag of another workspace and an unknown one are the same `404 not_found`, and the list holds the caller's tags only. The name is 1–40 characters after the whitespace around it is removed, stored as entered, and unique per owner without regard to case; creating or renaming to a name the caller already uses on another tag is `409 name_taken` (`errors: [{ path: "name", code: "name_taken" }]`) and writes nothing. `POST` answers `201` with `{ id, name, bookmarkCount, createdAt }`; `PATCH` takes `{ name }` (a closed object), answers `200` with the tag, and a name the tag has already, spelled the same, writes nothing; tags carry no `version`, so neither operation takes `If-Match`. `GET /tags` takes `sort` (`name`, the default, or `count`, most bookmarks first then by name), `limit` (default 50, at most 100) and `cursor` (§6.1), and answers `{ items, nextCursor, total }` (`total` exact up to 10 000, then `null` with `totalAtLeast: 10000`, Q42) with a page of the caller's tags and `bookmarkCount`, the number of each one's bookmarks that are not plan-archived; the cursor is bound to the account, the workspace and the sort, and any other is `400 bad_request`. `DELETE` answers `204`, removes the tag's links to bookmarks (the bookmarks stay) and keeps no tombstone, so the repeat is `404`. A folder is its owner's (doc 02 §7.1, doc 05 §2.4): another member's folder, a folder of another workspace and an unknown one are the same `404 not_found`, and the list holds the caller's folders only. The name is 1–64 characters after the whitespace around it is removed, stored as entered, and unique per owner without regard to case; creating or renaming to a name the caller already uses on another folder is `409 name_taken` (`errors: [{ path: "name", code: "name_taken" }]`) and writes nothing. `icon` is one of the sixty lucide names `FOLDER_ICONS` publishes in `@slugbase/contracts` (default `folder`) and `color` is an integer from 1 to 8, the number of the `--folder-N` theme token (default 1); anything else is `422 validation_failed`. A folder is `{ id, ownerId, name, icon, color, bookmarkCount, version, createdAt, updatedAt }`, `bookmarkCount` being the bookmarks filed in it that are not plan-archived. `POST` answers `201`. `GET /folders` takes `scope` (`all` or `mine`, both the caller's own folders until sharing arrives, when `shared` is added), `q` (a part of the name, without regard to case, 1–64 characters after trimming), `sort` (`name`, `count` — most bookmarks first, then by name —, `updated` — last changed first —, each with the identifier as tiebreak), `limit` (default 50, at most 100) and `cursor`, and answers `{ items, nextCursor, total }` as §6.1 describes, with `total` exact up to 10 000 and `null` with `totalAtLeast: 10000` above (Q42); the cursor is signed for the account, the workspace, the scope, the search and the sort it was issued for, and any other is `400 bad_request`. `GET` and `PATCH` answer the version as `ETag`; `PATCH` is a JSON Merge Patch of `name`, `icon` and `color`, takes `If-Match` (a version other than the current one is `412 precondition_failed` and nothing is written; without the header the patch applies), and a patch that names the values the folder has answers `200` with the unchanged `ETag`. `DELETE` answers `204`; the bookmarks stay and only their filings go, and the repeat is `404`.

A folder or a bookmark that is another member's, another workspace's or unknown, and a bookmark that is plan-archived when filing, is `404 not_found`, and then none of the bookmarks is filed or unfiled; a plan-archived bookmark may be taken out. A request is one transaction, all or nothing, and repeating it changes nothing (a bookmark already in the folder stays, one not in it is left). Filing moves no version of the folder or of the bookmarks. Both take the `write` token scope; a body that is empty, names more than 1 000 identifiers or a malformed one, or a field the operation does not declare is `422 validation_failed`.

Changing the flag deletes every session of the target; disabling deletes every session and the account's API tokens are refused by their lookup while it is disabled; the "account disabled" email is queued when mail is configured. A field that already has the value changes nothing and writes no event. Written to the instance audit stream as `instance.account_admin_granted`, `instance.account_admin_revoked`, `instance.account_disabled`, `instance.account_enabled` and `instance.account_email_verified`, each with the account as its entity and no metadata | ✓ |

| POST | `/instance/accounts/{id}/mfa-reset` | Remove MFA (documented recovery, doc 02 §2.7), without a body: `204`. In one transaction it clears the secret, the activation time and the accepted step, deletes the backup codes and every session of the account (partial ones included), writes `instance.account_mfa_reset` (the account as entity, no metadata) and, where mail is configured, queues the "an administrator reset your two-factor authentication" email (EN and DE); the secret is never read, returned or copied, and the account then signs in with its password alone. An account with no confirmed second factor changes nothing and still answers `204`, so a second admin who asks after the first writes no second event and sends no second email. `404` for an account that does not exist; `422 validation_failed` with the field code `account_disabled` on `id` for a disabled account, and `self` for the calling admin's own account (their second factor is turned off with the second factor, doc 10 T17), with nothing written | ✓ |
| POST | `/instance/accounts/{id}/password-reset-link` | Issue a one-hour reset link: mailed when mail is configured, otherwise returned once. Without a body, `200 { delivery, link }`: with mail `delivery` is `mail`, `link` is `null` and the ordinary password-reset email is queued (the mail job makes the token); without mail `delivery` is `link` and `link` is `<APP_ORIGIN>/reset-password#token=…`, valid for one hour and one use, shown here once (only its hash is stored, T7) and replacing the account's earlier unused reset token. Either way `instance.account_reset_link_issued` is written with the metadata `delivery` (`mail` or `link`) and never the token. In one transaction it reads the account's scope under the locks of `sys_instance_account_deletion_scope`, refuses with `409 last_owner` while the account is the only owner of a workspace that has other members (the problem document lists each such workspace as `workspaces: [{ id, name }]`), asks the deletion guard with `requestedBy: instanceAdmin` for the account and for every workspace that would be deleted with it, naming the account that is deleted (a refusal is its code, `409 billing_active`; a guard that throws or times out is `503`), and then deletes the account, marks the workspaces where it was the only member and queues their `workspace.delete` jobs and `account.deleted`, and writes `instance.account_deleted` (the account's identifier as entity, no address, no metadata); a refusal changes and writes nothing. `404` for an account that does not exist; `422 validation_failed` with the field code `last_instance_admin` on `id` when the account is the only enabled instance admin, and `self` on `id` for the calling admin's own account, which `DELETE /me` deletes (it asks for the typed address and ends the session, which this route does not).
