# SlugBase — API

The HTTP API is the whole product surface: the SPA, the Cloud operator console's product views, API-token scripts and any future browser extension use the same operations. Nothing the UI does is unavailable to an API-token caller with the same rights, and there are no undocumented endpoints (D12).

---

## 1. Contract and tooling

### 1.1 Code-first, generated, committed

| Job | Tool |
|---|---|
| Operation definitions (method, path, params, request and response bodies, errors, security, rate bucket, required role/entitlement) | `defineOperation()` in `@slugbase/contracts`, one file per tag under `packages/contracts/src/operations/`, with Zod 4 schemas. Omitting the policy fields is a compile error and a generator error that names the operation |
| Shared schemas (Bookmark, Folder, Problem, Page, …) | `@slugbase/contracts` — Zod schemas only; `zod` is its only runtime dependency, and it is importable by the server, the web app and the console |
| Route registration | Handlers live in `packages/server/src/routes/<domain>/` and are typed from the operation's request and response schemas; `register.ts` turns an operation and a handler into a Hono route and refuses at startup an operation that has no policy, is absent from the committed document or is registered twice |
| OpenAPI document | Generated by `pnpm api:gen` into `packages/contracts/generated/openapi.json` (CE) and, in the Cloud build, a merged `openapi.cloud.json` that adds the Cloud modules' operations — **committed** |
| Typed client | `openapi-typescript` (types into `packages/contracts/generated/schema.d.ts`, committed) + `openapi-fetch` runtime wrapper in `packages/web/src/api/client.ts` |
| Lint | Spectral with a SlugBase ruleset: every operation has an `operationId`, a tag, `x-slugbase-auth`, `x-slugbase-rate`, at least one 4xx `application/problem+json` response, and no inline anonymous object schemas in responses |
| Breaking-change check | `oasdiff breaking` against the committed document at the latest release tag reachable from `main`; a breaking change in `/api/v1` fails CI (§2.2) |
| Exported-API reports | API Extractor writes `packages/*/etc/*.api.md` per package; a changed report is a contract change (doc 09 §3.3) |

**Drift check:** `pnpm contracts:check` regenerates `openapi.json`, `schema.d.ts` and the API Extractor reports and fails when the working tree differs. A route whose handler returns a body the response schema doesn't describe fails its contract test (§1.3) — the generated document can never describe an API the server doesn't serve.

### 1.2 The operation declaration carries the policy

Every operation declares, next to its schemas:

```ts
defineOperation({
  method: 'post', path: '/bookmarks', tag: 'bookmarks', operationId: 'createBookmark',
  auth: 'member',            // x-slugbase-auth: anonymous | account | member | admin | owner | instanceAdmin | machine
  entitlement: undefined,    // x-slugbase-entitlement, e.g. 'sharing.teams'
  rate: 'write',             // x-slugbase-rate: bucket from §7, or 'none' for probes and machine routes
  scope: 'write',            // x-slugbase-scope: API-token scope required, read | write; absent = not token-callable
  reauth: false,             // true = needs a fresh re-authentication (§4.4)
  request: { body: BookmarkCreate },   // strict: unknown fields are a 422
  responses: { 201: …, 400: problem, 403: problem, 409: problem, 422: problem },
})
```

The authorization middleware (doc 01 §4, step 9) reads these extensions — the policy is data the OpenAPI document publishes, not a decorator hidden in a handler. The generator and Spectral reject an operation without them, and the server refuses to start when a registered route's policy differs from the committed document. An operation without `scope` is not token-callable: a bearer request to it answers `403 forbidden`.

### 1.3 Contract tests

The integration suite (doc 08 §4) walks the generated document and, for every operation: calls it with a valid fixture and validates the response against its declared schema; calls it unauthenticated, with a too-low role, without the entitlement (Cloud entitlement source fixture) and with a read-only token on a write route, and asserts the declared 401/403 problem type; calls it from workspace B on workspace A's resource and asserts 404.

### 1.4 Reference docs

`GET /api/v1/openapi.json` serves the committed document byte for byte; `/api/docs` serves a Scalar reference UI from bundled assets (no CDN, CSP-compatible). Both can be disabled with `API_DOCS_ENABLED=false` (they then answer `404 not_found`; `/api/config` is unaffected); both are on by default in CE and Cloud (the API is public, its document is not a secret).

## 2. Conventions

### 2.1 Paths

| Prefix | Contents |
|---|---|
| `/api/v1/*` | The versioned JSON API |
| `/api/config` | Unversioned bootstrap config for the SPA (§9.1) |
| `/api/docs` | The API reference UI (§1.4) |
| `/go/<slug>` | Slug forwarding (§9.3) — not under `/api`, because it is typed into the address bar |
| `/opensearch.xml` | OpenSearch description so browsers can add SlugBase as a search engine (§9.4) |
| `/health`, `/ready`, `/version` | Process probes (§9.2) — unversioned, never behind auth |
| `/metrics` | Internal listener on its own port only, never on the public listener (which answers `404 not_found`) |
| everything else | The SPA, served from the web root the composition passes to the server (`webRoot`): content-hashed assets with `Cache-Control: public, max-age=31536000, immutable`, `index.html` with `no-cache`; `index.html` for any unknown `GET` with `Accept: text/html`; a `404 not_found` problem for an unknown path under `/api/` or `/go/` or without an HTML `Accept`. Only `GET` and `HEAD` are served |

Path segments are lower-case kebab nouns, plural for collections (`/bookmarks`, `/api-tokens`, `/audit-events`). The active workspace is **never** in the path (D11, doc 01 §5) — `/bookmarks` means "bookmarks in the active workspace". The few account-level resources live under `/me`; CE instance administration under `/instance`.

Actions that are not CRUD use a sub-resource noun (`POST /bookmarks/{id}/open`, `POST /invitations/accept`), never verbs in the collection path and never `?action=`.

### 2.2 Versioning

- `/api/v1` is the only version at launch. **Additive changes** (new operation, new optional request field, new response field, new enum value in a response marked `x-extensible-enum`) ship in `v1` without notice. Clients must ignore unknown response fields; the generated client does.
- **Breaking changes** (removed or renamed field, new required request field, narrowed type, changed status code semantics) go to a new `/api/v2` served **alongside** `v1` for at least six months, announced in the changelog and via a `Deprecation` + `Sunset` header on every `v1` response of the affected operations.
- The SPA always targets the newest version and ships with the server, so it never needs the overlap; the overlap is for API-token users and the browser extension (post-1.0).
- `oasdiff` enforces this mechanically (§1.1).

### 2.3 Representation

| Rule | Value |
|---|---|
| Media type | `application/json; charset=utf-8` for requests and responses; `application/problem+json` for errors; `multipart/form-data` only on the Netscape import upload |
| Field casing | `camelCase` in JSON; `snake_case` in the database; mapping lives in the repository layer |
| IDs | UUIDv7, lower-case hyphenated strings (`0192f1c4-…`); generated in the application, never by a database function (Q91); time-ordered, so they double as a creation-order tiebreak in keyset pagination. No sequential integers are ever exposed |
| Timestamps | RFC 3339 UTC with millisecond precision (`2026-10-08T09:51:26.123Z`); `timestamptz` in the database |
| Absent vs null | Optional fields are omitted when unset in requests; responses always include declared fields, `null` when empty. `PATCH` distinguishes "omitted" (unchanged) from `null` (clear) |
| Money (Cloud) | Integer minor units plus an ISO 4217 currency code — never floats, never formatted strings in the API |
| Enums | Lower-case snake strings (`owner`, `shared_with_me`, `past_due`) |
| Booleans | Never stringly typed; query-string booleans are `true`/`false` only |
| Unknown fields | Rejected with `422 validation_failed` (Zod `strict`) — a typo never silently does nothing |
| Locale | Problem `detail` is always English (doc 02 §15); the SPA renders localised text from `code`. The account locale and `Accept-Language` affect only emails; data is locale-independent |

### 2.4 HTTP semantics

- `GET` is safe and never changes state (the single exception, recording usage on `/go`, happens asynchronously and is not observable in the response).
- `POST` creates (201 + `Location` + body) or performs an action (200/202/204).
- `PATCH` is JSON Merge Patch semantics on declared fields; `PUT` replaces a whole set (`PUT /teams/{id}/members`).
- `DELETE` answers `204`. Repeating it answers `204` only where the record keeps a state after the first call (a revoked API token, a revoked invitation); a hard-deleted resource (bookmark, folder, tag, team, share) keeps no tombstone, so a repeat is `404 not_found`. A resource the caller never could see is `404` as well.
- **Not found vs forbidden:** a resource in another workspace, or one the caller has no read access to, is **404** — existence is never disclosed. **403** is returned only when the caller can see the resource but may not perform the action (a member deleting a bookmark shared with them).
- **Optimistic concurrency** on editable records: every bookmark, folder, team and workspace response carries `version` (an integer) and an `ETag`; `PATCH`/`PUT` accept `If-Match` and return `412 precondition_failed` on mismatch. The SPA sends it from the edit modal so two tabs don't silently overwrite each other. Optional for API-token callers.

## 3. Errors

### 3.1 Shape

Every error is an RFC 9457 problem document:

```json
{
  "type": "https://slugbase.app/problems/slug_taken",
  "title": "Slug already in use",
  "status": 409,
  "code": "slug_taken",
  "detail": "You already use the slug \"mail\" in this workspace.",
  "requestId": "01J9…",
  "errors": [ { "path": "slug", "code": "slug_taken" } ]
}
```

- `code` is the stable machine identifier; `type` is its URL form; `title` is static per code (English); `detail` is English and may contain user-supplied values (escaped by the client). The SPA renders localised text from `code`.
- `errors[]` appears on `validation_failed` and on per-field domain errors, with JSON-pointer-ish `path`s matching the request body.
- `requestId` echoes the `X-Request-Id` response header for support.
- **Never** a stack trace, SQL, an internal identifier the caller couldn't already see, or a hint that distinguishes "no such account" from "wrong password".

### 3.2 Code catalog

| Status | `code` | When |
|---|---|---|
| 400 | `bad_request` | Malformed JSON, or a pagination cursor that does not match the request (§6.1) |
| 401 | `unauthenticated` | No valid session or token; also the one generic answer to sign-in with an unknown email, a wrong password or a disabled account, and to a revoked, expired or disabled-account token |
| 401 | `mfa_required` | Session exists at `partial` level; complete `POST /auth/mfa/verify` |
| 401 | `reauth_required` | Sensitive operation needs a fresh re-authentication (§4.4) |
| 403 | `forbidden` | Authenticated, can see the resource, may not do this; also a bearer request to an operation that is not token-callable, and an instance-admin operation without MFA enrolled |
| 403 | `registration_refused` | A deployment's registration policy refused this sign-up (doc 01 §13); the response is the same for every refusal reason |
| 403 | `cross_site_request` | Origin / Fetch-Metadata / content-type check failed (§5) |
| 403 | `token_scope` | API token has `read` scope on a write operation |
| 403 | `entitlement_required` | Plan doesn't include the feature; body carries `entitlement` and, on Cloud, `upgradeAvailable: true` |
| 403 | `email_unverified` | Verification is required and the account is unverified (sign-in with a correct password creates no session; Cloud actions that need a verified email) |
| 403 | `registration_closed` | Public registration is off |
| 403 | `setup_completed` | `POST /setup` after setup, or with setup turned off |
| 404 | `not_found` | Unknown, or not visible to the caller (§2.4) |
| 404 | `slug_not_found` | `/go` and `POST /go/choose`: no accessible forwarding bookmark |
| 409 | `slug_taken` | The caller already uses this slug in the workspace |
| 409 | `name_taken` | Folder, tag, team or API-token name already exists for that owner/workspace |
| 409 | `email_taken` | Invitation accept with registration fields for an email that already has an account — **only** where the flow is not enumeration-sensitive; registration and email change respond generically instead (doc 02 §2) |
| 409 | `already_member` | Invitation for, or accept by, an existing member; an instance admin adding themselves to a workspace they already belong to |
| 409 | `last_owner` | Removing, demoting or the departure of the last owner; deleting an account that is the only owner of a workspace with other members (the body lists the blocking workspaces by id and name) |
| 409 | `idempotency_conflict` | Same `Idempotency-Key` with a different request body (§6.3) |
| 409 | `billing_active` | A deployment extension refuses deleting a workspace or account (Cloud: it owns an active paid subscription); CE composes no such guard |
| 410 | `token_expired` | Verification, reset, email-change or invitation token unknown, expired, used or revoked — one identical answer |
| 412 | `precondition_failed` | `If-Match` mismatch |
| 413 | `payload_too_large` | Body over the route limit (default 64 KiB; the import routes allow 5 MiB) |
| 415 | `unsupported_media_type` | A bearer request whose mutation is not JSON (cookie and anonymous requests get `cross_site_request`, §5) |
| 422 | `validation_failed` | Schema validation; `errors[]` lists fields |
| 422 | `bookmark_limit_reached` | Create would exceed the bookmark cap; carries `limit` and `used`. Import never returns it: it adds up to the limit and reports the rest as skipped |
| 422 | `seat_limit_reached` | Invitation accept with no free seat (Cloud) |
| 422 | `workspace_limit_reached` | Creating a workspace beyond the account entitlement; carries `limit`, `used` and `upgradeAvailable` |
| 422 | `weak_password` | Fails length/breach policy (Q15); `errors[]` codes `too_short`, `too_long`, `breached` |
| 422 | `invalid_code` | Wrong or replayed TOTP or backup code (counts against the MFA bucket) |
| 422 | `url_not_allowed` | URL scheme not `http`/`https`, or host fails egress policy for a fetch |
| 429 | `rate_limited` | With `Retry-After` and `RateLimit-*` headers (§7) |
| 502 | `upstream_failed` | Metadata/AI/billing provider failed; the operation is retryable |
| 503 | `unavailable` | Not ready (migrations pending, DB unreachable), the rate-limit store failed, or the port is unconfigured (`mail_unavailable`, `ai_unavailable` as `code`) |
| 500 | `internal` | Everything else; logged with the request ID, reported through the error port |

Field codes inside `errors[]` of a `422 validation_failed` or a `403 forbidden`:

| Field code | Operation | Meaning |
|---|---|---|
| `api_token_limit_reached` | `POST /me/api-tokens` | The account already has 10 active tokens |
| `invitation_email_mismatch` | `POST /invitations/accept` | The signed-in account's verified email is not the invited address (`403 forbidden`) |
| `last_sign_in_method` | `DELETE /me/identities/{id}` | Would leave the account with no way to sign in |
| `last_instance_admin` | `PATCH` / `DELETE /instance/accounts/{id}` | Would leave the instance without an admin |

New codes are additive (§2.2); a client must treat an unknown `code` by its `status`.

## 4. Authentication

### 4.1 Principals

| Principal | Credential | Carries | Cross-site check (§5) | MFA |
|---|---|---|---|---|
| **Session** | `__Host-slugbase_session` cookie (`slugbase_session` without `Secure` when `APP_ORIGIN` is http) | account, active workspace, auth level (`partial` → `full`), re-auth timestamp | Required on unsafe methods | Enforced at login |
| **API token** | `Authorization: Bearer slb_<43 base62 characters>` (32 random bytes) | account, **bound workspace**, scope (`read` / `read-write`) | Not applied (no ambient credential) | Not applicable (an already-trusted credential, D10) |
| **Machine** | Route-specific: a module's inbound event endpoint (in Cloud, the billing service's events; no session; sender signature verified, idempotent), internal metrics port | nothing | Not applied | — |
| **Anonymous** | none | — | Required on unsafe methods (login, register, setup, password reset, invitation accept) | — |

When an `Authorization` header is present, cookies are **ignored** for that request — a request is either a token request or a browser request, never both. A bearer header that no resolver accepts is `401 unauthenticated` without falling back to a cookie.

### 4.2 API tokens and workspaces

A token is created by a member for one workspace they belong to (default: the active one) and **bound** to it: every request made with it acts in that workspace, with the account's current role there, regardless of the account's session. A token cannot switch workspaces and is accepted only by operations that declare a scope (the † marker in §10) — token management, sessions, MFA, email, password, account deletion and `/instance/*` declare none, so a token gets `403 forbidden` there. A member who loses membership loses every token bound to that workspace (deleted in the same transaction as the membership; the token's next request is `401`). Tokens of a disabled account are inert (`401`).

Multi-workspace automation uses one token per workspace. An `X-Slugbase-Workspace` header override is **not** offered at v1 (Q40).

### 4.3 Session levels

- `partial`: password verified, TOTP pending. Only `POST /auth/mfa/verify`, `POST /auth/logout` and `GET /api/config` accept it; everything else returns `401 mfa_required`. Expires after 5 minutes; five failed codes revoke it.
- `full`: signed in. The session token is **rotated** on sign-in, on the `partial → full` transition and on every privilege change (role change of the account itself in the active workspace, instance-admin flag change, password change, MFA enabled or disabled).

### 4.4 Re-authentication ("sudo mode")

Destructive or credential-changing operations require `reauthAt` within the last 10 minutes on the session (the `Re` column of §10): change password, remove password, change email, start MFA enrolment, disable MFA, regenerate backup codes, create an API token, unlink a sign-in method, delete the account, delete a workspace, transfer ownership, and the instance-admin operations marked ✓. Without it they return `401 reauth_required`; the SPA prompts for the password or a TOTP code via `POST /me/reauth` (accounts without a password re-authenticate through the provider: `GET /auth/oidc/{provider}/start?intent=reauth`) and retries.

### 4.5 Sign-in flows (shape only — behaviour in doc 02 §2)

| Flow | Calls |
|---|---|
| Password | `POST /auth/login` → `200 { next: "done" }` or `{ next: "mfa" }` (partial session) → `POST /auth/mfa/verify`. Unknown email, wrong password and disabled account are one `401`; an unverified account gets `403 email_unverified` when verification is required |
| OIDC | `GET /auth/oidc/{provider}/start?returnTo=&intent=` → `302` to IdP (state, nonce, PKCE stored server-side, doc 05 §2.1) → `GET /auth/oidc/{provider}/callback` → `302` to `returnTo` (same-origin paths only). `intent` is `login` (default), `link` (add the identity to the signed-in account), `reauth` (satisfy `POST /me/reauth` for a passwordless account) or `invite` (with `invitation=<token>`: accept that invitation through the provider). `link` and `reauth` need a full session; any failure ends on `/login` with one generic code |
| Registration (if enabled) | `POST /auth/register` → generic `202` → email link `/verify-email#token=…` (fragment, so the token never reaches server logs or `Referer`) → SPA calls `POST /auth/verify-email`, which verifies the account, creates its personal workspace and signs it in |
| Password reset | `POST /auth/password/forgot` → generic `202` → link `/reset-password#token=…` → `POST /auth/password/reset` (revokes every session of the account and creates a fresh one, `partial` when the account has MFA) |
| Email change | `POST /me/email` → link to the new address `…#token=…` → `POST /me/email/confirm`; the old address gets a notice whose "this wasn't me" link calls `POST /me/email/cancel` (cancels the change and revokes every session) |
| Invitation | `POST /invitations/inspect` → `POST /invitations/accept`: as the signed-in invitee, with registration fields for a new account, or through a provider (`intent=invite`) |
| First run (CE) | `GET /setup/status` → `POST /setup` (single-shot, advisory-locked, doc 05 §3.3; a one-time setup token printed to the server log when `SETUP_TOKEN_REQUIRED`) |

## 5. Cross-site request rules

Applied by middleware before routing (doc 01 §4, step 5) to every `POST`, `PUT`, `PATCH` and `DELETE` that is **not** bearer-authenticated and not a `machine` route:

1. `Origin` must be present and equal `APP_ORIGIN` exactly (scheme, host, port). A missing `Origin` on an unsafe method is rejected.
2. `Sec-Fetch-Site`, when present, must be `same-origin`.
3. `Content-Type` must be `application/json`, except the Netscape import route (`multipart/form-data`). This makes every mutation a non-simple request a cross-site HTML form cannot produce.

Failure is `403 cross_site_request`, logged at `warn` with the offending origin. This step owns the content-type rule for every cookie-authenticated and anonymous request; bearer requests skip it, and for them a non-JSON mutation is `415 unsupported_media_type` (body-limit stage). There is **no exemption list** (Q5): login, logout, registration, setup, MFA and reset are protected exactly like everything else, because they are all same-origin calls from the SPA.

No CORS headers are ever emitted on `/api/*`; preflights get `403`. Forms on a separate marketing origin therefore do **not** call the app origin from the browser: the marketing site proxies them same-origin to the server over the internal network, and their routes declare `audience: 'marketing-form'` (Q41; doc 01 §4 step 5).

`GET /go/<slug>` is a safe method and relies on `SameSite=Lax` (sent on top-level navigation from the address bar, not on cross-site subresource requests) plus the fact that it has no side effects beyond the asynchronous usage counter.

## 6. Collections

### 6.1 Keyset pagination

Every list operation is cursor-paginated; there is no offset pagination anywhere.

```
GET /api/v1/bookmarks?sort=recent&limit=48&cursor=eyJr…
→ { "items": [ … ], "nextCursor": "eyJr…" | null, "total": 1234 | null }
```

- `limit`: default per resource (bookmarks 48, others 50), maximum 100.
- `cursor`: opaque, base64url JSON of the last item's sort key and `id`, **HMAC-signed** with a purpose-bound subkey derived from the server secret (no extra key to configure) so a client can't forge positions or smuggle filter changes; a cursor is valid only with the filter, search text and sort it was issued for (mismatch → `400 bad_request`).
- `total`: returned for bookmarks, folders and tags lists (the UI shows counts), computed by a `count(*)` over the same filter — capped: above 10 000 it returns `null` and `totalAtLeast: 10000` (Q42).
- The UI's page selector (24/48/96) maps to `limit`; "page N of M" is replaced by "load more" and a count, because keyset pagination has no random page access. The design prototype's pager is adapted accordingly (doc 03).

### 6.2 Filtering and sorting

Filters are query parameters named after fields, validated by Zod; repeated keys for multi-value (`?tag=a&tag=b` — AND semantics for tags, OR is not offered). Sorting is `sort=<key>` from a per-resource allowlist; direction is part of the key (`recent`, `oldest`, `title_asc`, `title_desc`, `most_used`, `recently_opened`). Free-text is always `q`.

"Select all across pages" uses `GET /bookmarks/ids` with the same filters, returning up to 5 000 IDs (the select-all cap, config, doc 02 §16); bulk operations accept either an ID list (≤ 1 000) or the same filter object, and a filter matching more than the cap is `422 validation_failed`, so the server never needs the client to round-trip thousands of IDs (§10.6).

### 6.3 Idempotency keys

Operations that create billable or externally visible effects accept `Idempotency-Key` (a client-generated UUID): **required** on the billable mutations a module declares (in Cloud: checkout, seat changes and cancellation, Cloud doc 06); **accepted** on `POST /invitations`, `POST /import/*`, `POST /bookmarks`. The server stores `(account, key, operation, request hash) → response` for 24 hours (doc 05 §2.10); a replay returns the stored response with `Idempotency-Replayed: true`; the same key with a different body is `409 idempotency_conflict`; a concurrent duplicate waits on the first via a row lock rather than running twice. The mechanism is a route-level option an operation declares; keys are scoped to the account, so the same UUID used by two accounts never collides.

## 7. Rate limits

Token buckets through `RateLimitPort` (doc 01 §8.2). Keys combine the bucket with the client IP (as resolved through trusted proxies) and, when authenticated, the account ID — whichever bucket empties first wins. Responses carry `RateLimit-Policy`, `RateLimit` (IETF draft headers) and, on 429, `Retry-After`.

This table is the single list of defaults; doc 02 §16 shows the same values.

| Bucket | Applies to | Limit (per IP) | Limit (per account / target) |
|---|---|---|---|
| `login` | `POST /auth/login`, `GET /auth/oidc/{provider}/start`, `/callback` | 10 / min | 20 / hour per **email** (counted even for unknown emails) |
| `mfa` | `POST /auth/mfa/verify`, `POST /me/reauth` (TOTP), `POST /me/mfa/enrollment/confirm` | 10 / min | 5 failures per pending session (then the session is revoked); 30 / hour per account |
| `register` | `POST /auth/register` | 5 / hour | — |
| `reset` | `POST /auth/password/forgot`, `/auth/verify-email/resend`, `POST /me/email`, `POST /invitations/{id}/resend` | 5 / hour | 3 / hour per target email |
| `token_redeem` | `POST /auth/verify-email`, `/auth/password/reset`, `/invitations/inspect`, `/invitations/accept`, `/me/email/confirm`, `/me/email/cancel` | 10 / hour | — |
| `token_create` | `POST /me/api-tokens` | — | 20 / hour |
| `setup` | `POST /setup` | 10 / hour | — |
| `go` | `GET /go/*`, `POST /go/resolve`, `POST /go/choose`, `GET /go/suggest`, `POST /bookmarks/{id}/open` | 600 / min | 300 / min |
| `read` | Every other authenticated `GET` | 1 200 / min | 1 200 / min |
| `write` | Every other authenticated mutation | 300 / min | 120 / min |
| `bulk` | `POST /bookmarks/bulk`, `/import/*`, `GET /export/*` | — | 20 / hour |
| `fetch` | `POST /bookmarks/metadata`, `GET /favicons/*` (cache misses only) | 120 / min | 60 / min |
| `ai` | `POST /ai/suggestions` | — | 60 / hour per account, 600 / hour per workspace |
| `public` | `GET /api/config`, `GET /setup/status`, `GET /opensearch.xml` and the public read operations modules declare | 300 / min | — |

All limits are configuration (`RATE_LIMIT_<BUCKET>_*`); the values above are the defaults. Modules may add their own buckets; the Cloud modules do (Cloud docs 06 and 07). Probes (`/health`, `/ready`, `/version`) and `machine` routes declare `x-slugbase-rate: none` and are not rate-limited by this port; a `machine` route is protected by its signature check and the deployment's edge rules. If the limiter's store fails, the request answers `503 unavailable` — credential endpoints are never left unthrottled.

## 8. Response headers

On every API response: `X-Request-Id`, `Cache-Control: no-store`, `Content-Type`, the security headers of doc 01 §4 step 2. An operation may declare its own cache policy in the contract; only `GET /api/config` (`public, max-age=60`, §9.1) and `GET /favicons/{host}` (`private`, long-lived) do. On collections: none beyond the body (no `Link` headers). On rate-limited routes: `RateLimit-*`. On editable records: `ETag`. On deprecated operations: `Deprecation`, `Sunset`, `Link: rel="deprecation"`.

## 9. Public and process endpoints

### 9.1 `GET /api/config`

Unauthenticated, cacheable for 60 s (`Cache-Control: public, max-age=60`; the per-operation override of §8), the only thing the SPA needs before sign-in:

```json
{
  "apiVersion": "v1",
  "origin": "https://app.slugbase.app",
  "product": { "name": "SlugBase", "version": "1.4.2" },
  "signIn": { "password": true, "registration": true, "oidc": [ { "slug": "google", "name": "Google" } ] },
  "setupRequired": false,
  "instance": { "displayName": "SlugBase", "signInNotice": null },
  "locales": ["en", "de"], "defaultLocale": "en",
  "features": { "mail": true, "ai": true, "billing": true, "analyticsConsentRequired": true },
  "legal": { "imprintUrl": "…", "privacyUrl": "…", "termsUrl": "…" }
}
```

The document starts small and grows additively (§2.2): `apiVersion`, `origin`, `product`, `locales`, `defaultLocale` and `features.mail` / `features.ai` exist from the first server; `signIn`, `setupRequired`, `instance`, `legal`, `features.billing` and `features.analyticsConsentRequired` are added by the features that can populate them. `signIn.oidc` lists only enabled providers that answered discovery, never a secret or a provider URL. `instance.displayName` and `instance.signInNotice` are the instance settings of §10.10; the notice is plain text and the sign-in page renders it as text only.

`features` reports **whether a port is configured**, never entitlements (those need a workspace — `GET /entitlements`). `billing: true` only means a non-no-op billing adapter is composed; the SPA uses it to decide whether to load the Cloud extension routes' data, not to branch product behaviour (D4).

### 9.2 Probes

| Endpoint | Returns | Notes |
|---|---|---|
| `GET /health` | `200 {"status":"ok"}` | Process alive; no DB access |
| `GET /ready` | `200` / `503` with `{ database, migrations: { expected, applied } }` | DB reachable and migrations at the build's level; a database ahead of the build logs a warning and stays ready. While the server migrates in-process (doc 05 §5.3) it is `503` and every other route answers `503 unavailable` |
| `GET /version` | `{ name, version, commit, builtAt }` and nothing else | Read from a build-info file generated at build time (development fallback); the deploy gate compares `version` (doc 07 §4) |

Probes are unauthenticated, not rate-limited and send `Cache-Control: no-store`.

### 9.3 `GET /go/<slug>`

Not part of `/api/v1`, but specified here because it is the product's main entry point. It is a browser navigation: a bearer token answers `401`, and the `go` bucket applies.

| Situation | Response |
|---|---|
| Not signed in | `302 /login?returnTo=/go/<slug>` (the sign-in pages honour `returnTo` only for a same-origin `/go/<valid slug>` path) |
| Partial session | `302 /login/mfa?returnTo=…` |
| Slug grammar invalid | SPA not-found page (`404`, HTML) |
| No accessible forwarding bookmark | SPA "slug not found" page (`404`, HTML) offering "create a bookmark with this slug" and, when the slug resolves in another workspace of the member, "switch and continue" (`otherWorkspaces`, §10.8) |
| Exactly one match, or a remembered preference | `302 <destination>` with `Referrer-Policy: no-referrer`, `Cache-Control: no-store`; usage recorded asynchronously |
| Several matches, no preference | SPA disambiguation page (`200`, HTML) at the same URL; the SPA calls `POST /api/v1/go/resolve` |
| Extra path or query after the slug (`/go/jira/PROJ-12`) | `404` slug-not-found page; path appending is post-v1 (Q43) |

The HTML pages carry `Cache-Control: no-store` and `Referrer-Policy: no-referrer` as well. Only `http:` and `https:` destinations are ever redirected to (enforced on write and re-checked on read); `javascript:`, `data:` and anything else is impossible by construction.

### 9.4 `GET /opensearch.xml`

Unauthenticated, `Content-Type: application/opensearchdescription+xml`, built only from `APP_ORIGIN` and the product name (never from the request's `Host` or `X-Forwarded-Host`) and no user data. Its search URL is `<origin>/go/{searchTerms}`; the SPA shell links it with `<link rel="search">` so browsers can offer SlugBase as a search engine in one click.
