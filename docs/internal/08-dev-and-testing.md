# SlugBase — Development Workflow and Testing

## The problem

SlugBase is built almost entirely by agents (D21). An agent's work is only as good as the signal it can verify against, so the test system is designed around three needs:

1. **One command that means "done".** `pnpm gate` in each repository is the whole verification signal the executor runs before committing, the verifier re-runs independently, and CI mirrors (§6). Anything that matters and can run locally is in it.
2. **The dangerous properties are tested where they are enforced.** Tenant isolation is enforced by Postgres row-level security (D8), so it is tested against a real Postgres — never against a mock that would pass by construction. The same goes for migrations, sessions and the SSRF guard.
3. **Parallel lanes don't collide.** `/orchestrate` runs several executors in separate scratch clones at once. Every test that touches a database gets its own database (§3.2), so lanes never share state.

## 1. Local development

### 1.1 Prerequisites

| Tool | Version | Why |
|---|---|---|
| Node.js | 24.2 or later 24.x (`.nvmrc`) | D5. The direct-entry checks use `import.meta.main`, added in Node 24.2.0. `package.json` `engines` and a `preinstall` check enforce it |
| pnpm | 10.x (`packageManager` field) | Installed with `npm i -g pnpm@10` or Corepack where available |
| Docker + Compose plugin | current | Development Postgres and Mailpit; integration tests; image builds |
| `actionlint` | current | Only for workflow changes |
| GitHub CLI (`gh`) | current | Issues, pull requests and workflow runs. CE needs no package-registry token (§1.6) |

The development host is the maintainer's WSL2 machine. Nothing in the dev loop requires a public hostname, a tunnel or a cloud service.

### 1.2 Services

`compose.dev.yml` (CE) starts the shared development services, used by every checkout and every scratch clone on the machine:

| Service | Image | Port | Purpose |
|---|---|---|---|
| `postgres` | `postgres:18` | `54329` | Development database `slugbase_dev`, plus a superuser the test harness uses to create per-test databases (§3.2) |
| `mailpit` | `axllent/mailpit` | `1025` SMTP, `8025` UI | Catches every mail the SMTP adapter sends |
| `pgbouncer` (profile `pooler`) | `edoburu/pgbouncer` | `64329` | PgBouncer in transaction mode in front of `postgres`, for the pooled test run (§3.2); started by `pnpm test:integration:pooled` and not by `pnpm dev:services` |

```bash
pnpm dev:services        # docker compose -f compose.dev.yml up -d --wait
pnpm dev:services:down
```

The port is deliberately not `5432`, so a developer's own Postgres never collides with it and an agent can never connect to the wrong one by default.

**Concurrent runs.** The stack serves several `pnpm test:integration` or `pnpm gate` runs at once, because each run holds a bounded number of connections. `packages/db` and `packages/server` run at most two test files at a time (`maxWorkers` in each package's `vitest.config.ts`), and the harness opens at most one superuser session, four `slugbase_app` and two owner connections per file (§3.2). One `pnpm test:integration` run peaked at 38 connections above what the stack held before it (sampled with `SELECT count(*) FROM pg_stat_activity WHERE backend_type = 'client backend'`). `compose.dev.yml` therefore starts Postgres with `max_connections=300`: three runs at that peak add up to about 115, which the Postgres default of 100 cannot hold, and the rest is room for the app, the worker and other sessions on the machine. The stack supports three concurrent runs. A change to `compose.dev.yml` applies when `pnpm dev:services` next recreates the container. If a run fails with `too many clients already` or `remaining connection slots are reserved`, the stack still has the old limit (`SHOW max_connections`).

**No crash durability.** `compose.dev.yml` starts this Postgres with `fsync=off`, `synchronous_commit=off` and `full_page_writes=off`. The cluster holds only disposable data: the development database can be seeded again and every test database is cloned from a template and dropped (§3.2). Without those settings each `DROP DATABASE` waits for an immediate checkpoint to reach the disk, which costs far more than the clone when several runs share the host. The price is that a crash of the container, Docker or the host can leave the cluster corrupt or without its last writes. When that happens, `docker compose -f compose.dev.yml down -v` followed by `pnpm dev:services` provisions it again. These settings belong to this file only. The `postgres` service of CI (§6) is a separate container that keeps the image defaults, and production and self-hosted Postgres are not configured here. Like `max_connections`, a change to them applies when the container is next recreated.

### 1.3 Running the app

```bash
pnpm install
pnpm dev:env             # copies .env.example to .env (gitignored) and fills generated dev SESSION_SECRET/ENCRYPTION_KEY
pnpm db:migrate          # applies the CE migration chain to slugbase_dev
pnpm db:seed             # demo instance: an admin and a member, a demo workspace of 300 bookmarks, a workspace of 5 000 (§1.4)
pnpm dev                 # turbo: server (watch), worker (watch), web (Vite)
```

**One origin in development too** (D11). Vite serves the SPA on `http://localhost:5173` and proxies `/api`, `/go` and `/health` to the server on `:3000`. The browser only ever sees `localhost:5173`, so the session cookie, the Origin check and `SameSite` behave exactly as in production. In development the cookie is named `slugbase_session` without the `__Host-` prefix and without `Secure` (browsers refuse `__Host-` on plain HTTP); the server derives both from `APP_ORIGIN`'s scheme, not from a mode flag.

`.env` is created from the committed `.env.example`, whose defaults match `compose.dev.yml`. It is gitignored and never committed, and `pnpm dev:env` refuses to overwrite an existing one. There is no secrets manager in the dev loop (D24). Production refuses to start with the dev defaults (doc 01 §11).

### 1.4 Seed data

`pnpm db:seed` builds a deterministic demo instance from `@slugbase/testing` factories (a fixed random seed and a fixed clock, so every run produces the same rows). The factories are plain data builders with no database in them: the seed script turns the instance into one SQL transaction, and the browser journeys import the same builders for their fixtures (`e2e/support/bookmark-fixtures.ts`).

The instance has two accounts (an instance admin and a member), a demo workspace of 300 bookmarks that both use, and a workspace of 5 000 bookmarks owned by the admin. Every workspace starts with the bookmark shapes that break UIs: a title and a description at their length limits and a URL of about 2 000 characters, a title with no break opportunity, a one-character title, Arabic, Hebrew and mixed-direction titles, emoji titles (a ZWJ sequence, a flag, a skin tone), titles and descriptions with markup-like text (`<img src=x onerror=alert(1)>`, `<script>`, HTML entities), pinned rows, rows with opens and rows without, and three URLs that differ and share one canonical form (doc 02 §5.1). The rest is filler with the same mix: about 4 % pinned, a little over half opened, a few percent emoji or right-to-left, and a few percent duplicate canonical URLs. Colliding slugs across members and via sharing, shared folders, an over-cap Free workspace, an account with MFA enrolled and an expired invitation are added by the epics that introduce them; the 50 000-bookmark performance instance belongs to the performance suite (§5.3).

**It writes through `slugbase_system`, not the application role.** The seed connects with `DATABASE_MIGRATE_URL` as `slugbase_migrator`, sets the role for its one transaction and creates the accounts and workspaces with the system operations the product uses (`sys_create_account`, `sys_create_workspace`). The application role cannot set a bookmark's usage (`open_count`, `last_opened_at`) and has no `UPDATE` on `workspaces.bookmark_count`, so the script inserts the bookmarks as the system role and then sets each workspace's `bookmark_count` to the number of its rows (doc 05 §2.2). `psql` must be on the `PATH`, as for the test harness; the script runs through it, so no database handle is created outside `packages/db`. Any failure rolls the whole script back, and a database that already holds one of the seeded addresses is refused as a whole.

**It refuses any database but the development one.** Before it connects, `DATABASE_URL` and `DATABASE_MIGRATE_URL` must both name host `127.0.0.1` (or `localhost`), port `54329` and the database `slugbase_dev`, the address `compose.dev.yml` publishes, with no connection options in the URL, and the migrate URL must connect as `slugbase_migrator`. A value that is unset, unparsable or anything else is a refusal, never a fallback, and the child process gets only that connection and the `PATH`, so a `PG*` variable of the caller cannot redirect it. The passwords are random, made when the command runs and shown once on its output; only their argon2id hashes are stored, in `slugbase_dev`, and they open no other database. To seed again, start from an empty development database (`docker compose -f compose.dev.yml down -v`, `pnpm dev:services`, `pnpm db:migrate`).

## 2. Test tiers

| Tier | What | Runs against | Where |
|---|---|---|---|
| **T1 Unit** | Pure logic: domain services with in-memory ports, entitlement engine, slug grammar, parsers, authorization policies, React components | Nothing external | Every package, `*.test.ts(x)` colocated |
| **T2 Integration** | Repositories, RLS, migrations, the HTTP chain end to end in-process, worker jobs, adapters against local fakes | Real PostgreSQL (per-test database): 18 locally, 17 and 18 in CI (Q3) | `packages/db`, `packages/server`, `packages/adapters`; the Cloud modules in the Cloud repository |
| **T3 Contract** | OpenAPI drift, API Extractor reports, client generation, i18n catalogs, forbidden terms | Generated artefacts vs committed ones | `pnpm contracts:check`, `pnpm i18n:check`, `pnpm lint` |
| **T4 E2E** | User journeys in a browser against the built image | Docker: image + Postgres + Mailpit (+ fakes of Cloud's external services in the Cloud repository) | `e2e/` in each repo |
| **T5 Non-functional** | Accessibility, load/latency budgets, migration timing on large data | Built app; seeded large dataset | Scheduled CI and before promotions (§5.3, §5.4) |

T1–T3 are in `pnpm gate`. T4 runs in CI on every push to `dev` and on promotion PRs, and locally on demand (`pnpm test:e2e`). T5 runs on a schedule and before a production promotion.

## 3. T1 and T2 in detail

### 3.1 Unit tests and in-memory ports

Every port (doc 01 §6) ships an in-memory implementation in `@slugbase/testing-ports` — `InMemoryMail` (captures messages), `FakeAi` (deterministic suggestions), `FakeIdentity` (a scripted OIDC provider), `FakeEgress` (scripted responses keyed by URL, including redirects to private addresses and oversized bodies), `FixedClock`, `SequenceIds`. Identifiers are generated in the application, not by a database function (Q91), so `SequenceIds` stands in for the generator and no test depends on a PostgreSQL-version-specific id function. Domain services are tested against these with no database. Unit tests must run in well under a minute for the whole repo; a test that needs Postgres is an integration test. `@slugbase/testing-ports` imports no workspace package, so `@slugbase/core` takes it as a development dependency and its unit tests import the fakes directly; `@slugbase/testing` re-exports it, so integration suites keep the single `@slugbase/testing` import. Because the package may not depend on `@slugbase/core` (a `core` → `testing-ports` → `core` edge is a package cycle that Turborepo rejects), a fake does not `implements` the port interface: the fakes are structurally typed, and the check that each satisfies its port lives in `@slugbase/testing`, which may import both. Only test files, `test/` folders and `apps/*` development tooling import it (doc 09 §2.1).

React components are tested with Testing Library and `vitest-axe` for component-level accessibility. The data layer in the web app is tested against **MSW handlers generated from `openapi.json`** (§7), so a contract change breaks the web tests in the same commit.

### 3.2 The Postgres test harness

`@slugbase/testing/db` gives every integration test file its own database:

1. On first use in a run, it creates `slugbase_tpl_<migrationhash>` by applying the migration chain once (CE, or the composed chain in the Cloud repository, doc 05 §5.5), installs the roles (`slugbase_app` without `BYPASSRLS`, `slugbase_system`) and marks it as a template. The hash is over the migration files, so a changed migration produces a new template automatically.
2. Each test file gets `CREATE DATABASE test_<random> TEMPLATE slugbase_tpl_<hash>` — tens of milliseconds — and drops it afterwards.
3. Tests connect as `slugbase_app` exactly like the server does. Only fixtures connect as the owner role, to insert data RLS would refuse.

The harness needs `SLUGBASE_TEST_PG_URL` (a superuser URL); it defaults to the `compose.dev.yml` Postgres. In CI it points at a service container (§6). Because databases are per file and named randomly, concurrent runs never collide with one another; how many runs fit at once is bounded by the connection limit of the dev Postgres, which supports three (§1.2).

**The pooled run.** `SLUGBASE_TEST_POOLER_URL` (`host:port`) puts a PgBouncer between the tests and the database. Like `SLUGBASE_TEST_PG_URL` it is a variable of the test harness and not of the application, so it is in neither the env schema nor doc 07's key inventory. When it is set, the `app` pool and `tenant` of every test database connect as `slugbase_app` through the pooler, and the owner pool, the template build and the cluster sessions stay direct; a test that builds its server's `DATABASE_URL` from `database.app` (the contract matrix) goes through the pooler with no change of its own. When it is unset the harness connects directly, and `pnpm test:integration` needs no pooler. The pooler is the `pgbouncer` service of `compose.dev.yml` under the profile `pooler`, so `pnpm dev:services` is unchanged (its configuration is in `packages/db/test/pooler/`): `pool_mode = transaction`, `default_pool_size = 1`, so every client of a test database is served by one Postgres backend and a setting that outlives its transaction is met by the next request, and `max_prepared_statements` as in the rig of `pnpm perf:go` (`packages/db/test/perf/rig/`). The image is pinned by tag and digest. Before the harness returns a database it reads the pooler's console (`SHOW POOLS`, `SHOW DATABASES`) and fails unless the pooler serves that database to `slugbase_app` in transaction mode with a pool of one connection, so a missing or different pooler is an error and never a quiet fall back to a direct connection.

`pnpm test:integration:pooled` starts the pooler, builds the packages the files import and runs three files with the variable set: `packages/db/test/pooler.integration.test.ts`, `packages/testing/test/tenancy-matrix.integration.test.ts` and `packages/server/test/contract/contract.integration.test.ts`. CI runs the same script as the job `integration-pooled` (§6.2). The first file runs only where the variable is set. Two clients run tenant transactions for different workspaces and accounts at the same time; the pooler serves them one transaction after the other on the one backend (asserted through `pg_backend_pid()`), and neither sees the other's rows. The next transaction on that backend after a `COMMIT` and after a `ROLLBACK` finds `app.account_id` and `app.workspace_id` empty. The same check is run against a test-only tenant transaction that sets the context for the session (`set_config(…, false)`), and must report the leak (T1). A tooling test (`tooling/test/advisory-locks.test.ts`) finds no session-level advisory lock in `packages/*/src/**` or `packages/db/src/sql/**` outside `migrate` and the harness (doc 01 §9.2).

Every changed migration, custom SQL file or `roles.sql` leaves one more template behind, and the harness never drops one on its own: scratch clones at different hashes run at the same time. `pnpm --filter @slugbase/db test:prune-templates` drops the `slugbase_tpl_*` templates that nothing uses (template names as arguments limit it to those). It never lists or touches a database outside the `slugbase_tpl_<hash>` names, and it keeps the template of the current hash and any template that is:

- being built or dropped (the per-template build lock, which the prune only tries and never waits for);
- cloned from, or about to be: Postgres records no link from `test_<random>` to its template, so every process holds a per-template *use* lock, shared, from before it looks for the template until its test database is dropped, and the prune only tries the exclusive one;
- connected to (and the `DROP DATABASE` has no `FORCE`, so a connection that opens late makes it fail and leaves the template marked).

A process that wants a template the prune has just dropped builds it again.

A run that is killed before its `afterAll` leaves its `test_<random>` database behind, and the harness drops only the databases it created itself, so leftovers are cleared by hand with `DROP DATABASE` once no run on the cluster is using them; they do not slow the creation of a test database.

Roles are cluster-wide, and every test database depends on them staying as `roles.sql` leaves them, so the harness keeps one advisory lock per cluster (the *cluster lock*) beside the per-template ones:

- **Shared, for as long as a process uses the cluster.** A process holds it, through one superuser session, from before its first test database exists until its last one is dropped. A test file that reads the roles without a database of its own (`migrate.integration.test.ts`, `roles.integration.test.ts`) holds it the same way through `useCluster()`. Any number of processes, in any number of runs, hold it at once, so holders of the shared lock never wait for one another.
- **Exclusive, for a step that commits a change to the roles.** `lockExclusive()` of `useCluster()` waits until no other process holds the lock, which includes every test database of every run, and gives the lock back (shared again) when the step is over. A process that has a test database of its own cannot take it, because it would wait for itself. No test takes it on the shared cluster lock (the tests of the lock itself, `harness-cluster-lock.integration.test.ts` and its `support/cluster-holder.ts`, take it in a scratch database of their own, where the advisory locks are separate): the drift test of `roles.integration.test.ts` makes its drift and converges it in one transaction (psql opens it, `roles.sql` commits it), and a session sees a role only once its transaction has committed, so no test database of another run ever meets the drift.
- **What an exclusive request costs.** A shared request queues behind an exclusive one that waits, so from the moment a step asks for the lock until it is over, the first test database of every process that does not yet hold the cluster waits, and that is every test file of every run, because a test file is a process of its own. The wait lasts until the test databases in use have been dropped, which is as long as the longest test file still running in any run on the cluster. Sampled from `pg_stat_activity` while two server runs shared the cluster with a run whose drift test took the lock exclusively, five test databases waited 131 to 137 s each in `pg_advisory_lock_shared`, behind one `pg_advisory_lock` that waited 139 s. A step that needs the lock therefore stays as short as it can, and a change that can be made and undone in one transaction needs no step at all. A process that already holds the cluster (it has a test database in use) asks again for nothing and creates more test databases without waiting. A test file never takes the lock by itself (`packages/db/test/integration-concurrency.test.ts` checks this), and `harness-cluster-lock.integration.test.ts` runs two harness users at once to show that a test database waits for the exclusive step and not for the rest of the file of the process that took it.

Three concurrent runs (§1.2) share one cluster lock this way.

### 3.3 The cross-tenant matrix (D8, doc 01 §5.5)

The single most important test in the codebase. It lives in `packages/testing/src/tenancy/` and runs in two modes:

- **API mode.** For every operation in `openapi.json`, with a fixture of two workspaces A and B (each with owner, admin, member, a team, shared and unshared bookmarks/folders/tags, slugs, invitations, tokens): authenticate as each principal of A and attempt the operation against every B identifier the fixture holds. Every attempt leaves B unchanged (a row-level checksum of B's tables before and after) and quotes nothing of B, and answers by role, from the operation's `x-slugbase-auth` level: a principal at or above the policy gets `404` (never `403` — existence is not disclosed); a principal below it (a member on an `admin` or `owner` operation, an admin on an `owner` one) gets the `403 forbidden` of stage 9 (doc 01 §4), which is decided before any lookup and so discloses nothing. The matrix still calls with every principal, so a `404` is asserted exactly where a lookup happens, and a handler that is reached by a principal below its policy fails the matrix.
- **RLS-only mode.** The same matrix against the repositories, but through a **test-only build of the repositories with the workspace predicate removed**, inside `withTenant(A)`. Every read must return no B rows and every write must fail. This proves that RLS alone holds the boundary (T1), independent of the application layer.

Both modes also run through the pooler of §3.2 (`pnpm test:integration:pooled`): every attempt against another workspace answers as above and leaves B's checksum unchanged with the tenant context set transaction-locally on a connection that PgBouncer shares between requests.

The matrix is **generated from the contract**, not written by hand per operation: a new operation is covered the moment it is declared, and an operation whose path parameters the generator cannot map to fixture identifiers fails the test until a mapping is added. Doc 10 T1 and T2 cite it; the risk review (doc 09 §5.3) requires it to be extended for any new repository method.

Within-workspace sharing rules (owner-only mutation, read via direct share, team share and shared folder; a member who leaves loses access) have their own table-driven suite in `packages/core` (unit, with a policy oracle) and `packages/server` (integration).

### 3.4 Migration tests

- **Fresh apply**: the template build (§3.2) applies the whole chain to an empty database on every run.
- **Upgrade with data**: `packages/db/test/migrations/` keeps a **fixture snapshot per released schema version** (a `pg_dump` of the seeded instance at that version, compressed, committed when a version is released). The test restores each snapshot, applies every later migration, then runs a read-back suite (row counts, invariants such as "every bookmark's slug is unique per owner", RLS still forced on every tenant table). A migration that loses or corrupts data fails here.
- **Policy lint** (`pnpm db:check`): every table with a `workspace_id` column has RLS enabled **and forced** and at least one policy; `slugbase_app` owns no table; no migration file changed after its first commit (each migration's SHA-256 is recorded in `packages/db/src/check/migration-checksums.json`; `pnpm db:record-checksums` adds the entry of a new migration after `pnpm db:generate`, and an existing entry is never rewritten); drizzle-kit reports no pending diff between schema and migrations.
- **Expand/contract check** (`pnpm db:check`, doc 05 §5.2): a migration added since the latest release tag that drops or renames a released column or table, or takes a rewriting step on one, is rejected unless it is the contract half of a pair. The leading comment block of the file holds the header `-- slugbase:contract expand=<migration tag> release=<version>` (`<version>` is a release tag, `MAJOR.MINOR.PATCH` with an optional pre-release suffix and optional leading `v`, whose release already contains the expand migration), which `pnpm db:generate --contract expand=<migration tag> release=<version>` writes so the recorded checksum covers it. The header alone decides, on every event: a valid one accepts the step, a missing or invalid one fails it, and the check reads no label or environment value. The maintainer approves a contract migration by merging the pull request that carries it, so a required status check never depends on a label. The check reads release tags and migration history from git, so it **fails in a shallow clone**: the `integration` job checks out with `fetch-depth: 0`, and a local clone runs `git fetch --unshallow --tags`. Tests: the rule against temporary git repositories (`packages/db/test/check/expand-contract.test.ts`), the command with and without a header, run with no environment set (`expand-contract.integration.test.ts`) and the generator option (`generate-migration.test.ts`).
- **The `migrate` command** (D25): two `migrate` processes started at once against the same database apply the chain exactly once (the advisory lock); `lock_timeout` makes a migration blocked by a held table lock fail fast instead of queueing; a failed migration leaves the version table unchanged and exits non-zero.
- **The two call sites** (D25):
  - **CE migrate-on-start:** the image entrypoint runs `migrate` with `DATABASE_MIGRATE_URL`, and only then starts the server with that URL removed from its environment (a failure exits non-zero before anything serves). A second replica waits on the lock and starts without re-applying. The in-process variant (`slugbase server --with-worker`, Q11, where no entrypoint step exists) migrates inside the process and serves `/health` and `/ready` first, with `/ready` answering `503` until the database is at the expected migration level.
  - **`MIGRATE_ON_START=false`** (a managed deployment that runs `migrate` as a separate step, as Cloud does): the server never runs migrations and refuses `/ready` until the database is at the migration level the build expects.

### 3.5 Security-focused integration suites

| Suite | Asserts |
|---|---|
| `http/cross-site` | Cookie-authenticated mutations without a matching `Origin`, with `Sec-Fetch-Site: cross-site`, or with a non-JSON content type are refused; bearer requests ignore cookies (T5) |
| `http/headers` | CSP, HSTS, COOP, Referrer-Policy per route; `no-store` on `/api` and `/go`, except an operation that declares its own cache lifetime (`GET /api/config`, 60 s) |
| `auth/enumeration` | Login, reset, registration and invitation endpoints return identical status, body shape and timing class for known and unknown emails (T8) |
| `auth/sessions` | Rotation on login, MFA and privilege change; revocation takes effect on the next request; hashes only at rest (T4) |
| `auth/rate-limits` | Limits hold per IP and per account; `X-Forwarded-For` beyond the trusted hops is ignored (T9) |
| `egress/ssrf` | Private, loopback, link-local, CGNAT, metadata, IPv6-mapped and DNS-rebinding targets are refused, including after redirects; size and time caps hold (T6); an instance built with `privateOrigin` (the AI adapter's, Q90) reaches that one origin on a loopback, private, CGNAT or unique-local address, resolved once and pinned, while the same request through an instance without it, the same host on another port or scheme, another private host, link-local, metadata, unspecified, multicast and reserved answers (alone or mixed with a private one, IPv4-mapped forms included), and a redirect from the origin to another private port, host or the metadata address stay refused with no connection; a redirect to the same origin is followed, one to a public host carries no `Authorization`, a 307 or 308 with a body to another origin is refused, origins match as `URL.origin` writes them (case, IPv4 notation, IDNA and the default port match, a trailing dot does not), and the size, time and content-type caps hold — against a local DNS stub and HTTP servers, never the internet |
| `go/resolution` | Only accessible, forwarding-enabled bookmarks resolve; non-http(s) destinations are never stored or redirected; disambiguation and remembered choices (T12) |
| `import/hostile` | Oversized, deeply nested, malformed and script-laden JSON/Netscape files are rejected or neutralised (T13) |
| `machine` routes | An event with a missing, wrong or stale signature changes nothing; duplicate deliveries apply once; an older event never overwrites newer state; no session or token principal is derived. Machine routes are not behind the rate-limit port (the signature check is their control, doc 04 §7). Cloud's billing-event suite extends this in the Cloud repository (T10) |

## 4. T3 — contracts and generated artefacts

- **OpenAPI drift**: `pnpm contracts:check` regenerates `packages/contracts/generated/openapi.json` and the typed client and fails on any diff. Generated files are committed so reviewers and Cloud see API changes as diffs.
- **API Extractor**: regenerates every package's `etc/*.api.md` and fails on diff (doc 09 §3.1).
- **i18n**: `pnpm i18n:check` — EN and DE catalogs have identical key sets, ICU messages parse, no unused keys, and a lint rule (`eslint-plugin-i18next`) flags literal strings in JSX and in user-facing server messages.
- **Forbidden terms** (CE only): the public-repo guard (doc 09 §4) runs in `pnpm lint`.
- **Vocabulary lint**: product-vocabulary violations (`organization`, `collection`, `favorite`) in identifiers and catalogs fail lint (doc 00 §3).

## 5. T4 and T5

### 5.1 E2E

Playwright against the **built image**, never against `pnpm dev`, so what is tested is what ships.

- **CE** (`slugbase/e2e/`): `docker run` the image + Postgres + Mailpit; journeys: first-run setup → invite → accept (mail read from Mailpit's API) → bookmarks, folders, tags, pinning → slug + `/go` + disambiguation → palette `go` mode → AI suggestions in the bookmark modal (a stand-in for the provider's endpoint, which records what the server sent it) → sharing via team → MFA enrol/login/backup code → API token → export → import into a fresh workspace (round-trip equality) → instance admin.

### 5.3 Performance budgets

A scheduled job (weekly, and before a production promotion) runs `k6` against the image, built from the commit under test and started with `server`, with a seeded large instance (50 000 bookmarks in one workspace, 2 000 workspaces): `/go` p95 < 30 ms server time, list and search p95 < 100 ms (doc 01 §9.3), with Postgres on the same runner. `pnpm perf` runs the same scenarios locally against the built server, or against an image with `--image`. The list is measured with no text and no filter (every sort, the first and a deep page), narrowed by a text (`GET /api/v1/bookmarks?q=`, the first and a deep page) and under a tag and under a folder (the first and a deep page of each), each with a budget of its own. The slug suggestions of the palette's `go` mode (`GET /api/v1/go/suggest`, p95 < 50 ms, doc 02 §6.2) are requested with the first character, the leading word and the whole of a slug of the seed, each with a budget of its own, and the dashboard (`GET /api/v1/dashboard`, the call of the home screen) holds p95 < 100 ms; a scenario whose budgets are of several shapes takes the shape of each arrival from its number, in turn, so that a run with at least as many arrivals per scenario as it has shapes (12 for the list, the most) requests every one; a shape with no request fails the run, naming it, and is never reported as a p95 of 0 ms. `/go` also requests the slugs of archived bookmarks, which it does not find. Before the budgets, 10 000 requests for one forwarding slug check that `/go` does not become write load: `bookmarks` may be updated once for each 10 s flush interval of the usage buffer (doc 01 §8.1) that began during them and once for the flush after them, and more is reported like an exceeded budget. The search budget holds because a search ranks the bookmarks whose slug and title hold every word of the query (all of them, through their own GIN index) and takes the bookmarks whose host or description completes the words from a bounded window to fill the remaining places: title and slug matches rank ahead of host- and description-only matches, and a word that matches most of a large library is not ranked in full (doc 02 §9.1, doc 05 §3.3). The integration suite holds the plan behind that budget on a 50 000-bookmark workspace in `packages/db/test/search-plan.integration.test.ts`, for a page of the bookmark list narrowed by a text with its count in `packages/db/test/bookmarks-list-search-plan.integration.test.ts`, for the dashboard in `packages/db/test/dashboard-plan.integration.test.ts`, for the list without a text in `packages/db/test/bookmarks-list-plan.integration.test.ts` and for the slug suggestions of the palette's `go` mode in `packages/db/test/go-suggest-plan.integration.test.ts`; the first three are in a vitest project of their own (`integration-quiet`) that the root `pnpm test:integration` runs by itself, after the integration suites of every package have finished, so that no other database-heavy file shares the machine with the times they report (the other two are in `integration`). A request for a page of a list that is narrowed by a text and nothing else calls `sys_bookmark_match` once and takes the total from the number of matches the page statement counted; a list narrowed by anything beside the text probes each match by the primary key to count them. The last phase imports the largest Netscape file and then the largest SlugBase JSON file (5 000 bookmarks each) into the large workspace while `/go` and the list are requested, and reports the p95 of both while an import is in flight (`scripts/perf/README.md`, "The import phase"): both have a budget of their own, and it is a **ratio to the same run's steady scenario** and not a limit in milliseconds: the p95 of `/go` while an import is in flight may be at most **5.9 times** the p95 of the steady `go` scenario of the same run, and the p95 of the list at most **5.8 times** the steady `list` p95 (`RATIO_BUDGETS` in `scripts/perf/budgets.js`); the steady budgets stay 30 ms and 100 ms. A ratio is what a member feels of another member's import, how much it slows `/go` and the list, and it cancels most of the speed of the runner machine, which a limit in milliseconds set from a few runs did not (decision of 2026-11-09, #810: the p95 of `/go` during an import was 26.89 to 67.10 ms in six runs, its ratio to the steady p95 of the same run 2.93 to 4.37). An import is synchronous and in-process (doc 02 §13.1), but its CPU work (the multipart decode of the 5 MiB body, the parse and validation of the file, the reading of each bookmark) runs in a worker thread of the server process; what the requests beside it still wait for is the request thread's share of the import (the worker's answer, the database questions and the batch writes) and the runner's CPUs, which the server, its worker thread, Postgres and k6 share. A ratio is judged by `scripts/perf/run.mjs` and not by k6, because its other side is the p95 of another k6 run (the import phase is a run of its own): the two import scenarios have a threshold that no value can fail, so k6 never ends the run on a limit that is no longer in milliseconds. A ratio is not judged when either side, the import scenario or the steady one, is saturated or dropped arrivals (the p95 of such a scenario is the time of a queue): the report says "not judged" and why, neither passing nor failing it. The report row and the "Performance budget exceeded: import" issue show both p95 in milliseconds, the ratio and its limit. Steady `/go` stays at 30 ms (doc 01 §9.3, doc 12 §5). The `performance` job's runner is the reference host for every budget, because the hosts that run SlugBase are unlikely to be much bigger than it and more likely smaller; a number measured on a large development host is optimistic and a proxy only. The two ratios follow the rule the millisecond budgets were set by, applied to the ratio: the highest counted ratio plus the spread between the highest and the lowest, rounded up to one decimal, over six `workflow_dispatch` runs of `nightly.yml` on `dev` at or after `dc5d3701` (the worker thread, #807), none saturated and none with a dropped arrival in `go`, `list`, `go_import` or `list_import`, so all six counted. Ratios of `go during import` over steady `go` (p95 in ms, ratio to two decimals): 30.30 / 10.01 = 3.03 ([42664296502](https://github.com/mdg-labs/slugbase/actions/runs/42664296502)), 42.17 / 12.23 = 3.45 ([42666060611](https://github.com/mdg-labs/slugbase/actions/runs/42666060611)), 36.44 / 11.52 = 3.16 ([42668101921](https://github.com/mdg-labs/slugbase/actions/runs/42668101921)), 67.10 / 15.37 = 4.37 ([42676896584](https://github.com/mdg-labs/slugbase/actions/runs/42676896584)), 26.89 / 9.17 = 2.93 ([42679115825](https://github.com/mdg-labs/slugbase/actions/runs/42679115825)) and 61.04 / 14.16 = 4.31 ([42680837660](https://github.com/mdg-labs/slugbase/actions/runs/42680837660)), so 4.37 + (4.37 - 2.93) = 5.81, rounded up to 5.9. `list during import` over steady `list`: 37.74 / 14.18 = 2.66, 54.94 / 16.13 = 3.41, 47.26 / 16.35 = 2.89, 84.00 / 21.15 = 3.97, 39.36 / 14.33 = 2.75 and 79.71 / 18.99 = 4.20, so 4.20 + (4.20 - 2.66) = 5.74, rounded up to 5.8. The first three runs of the import phase (`b7351d91`, before the worker thread: 85.61, 152.22 and 173.54 ms, the last saturated) predate #807 and are not counted. Change the ratios only from a new set of runner runs, by the same rule.

**How to read a `k6` run.** The scenarios are open-loop, so a server that serves fewer requests a second than the rate makes the rest wait, and `http_req_waiting` counts the wait: the p95 of a scenario that fell behind grows with its length and is the queue, not the time of a statement. The run therefore reports, with each scenario's budgets, the requests it completed, the arrivals `k6` dropped and the most VUs it used (`result.json`, the job summary and the issue body of `nightly.yml`), marks the scenario saturated when it dropped an arrival or used all 100 VUs, and reports the p95 of each list sort and page and of each search term (the seven `searchTerms` of the seed, which `tooling/test/perf-budgets.test.ts` holds `scripts/perf/budgets.js` to, and the shared slugs), so a regression names them. These are reported and never thresholds, so they cannot end `k6` with status 99; `scripts/perf/README.md` says how to find the rate a server keeps up with.

**What made `search` miss its budget.** `sys_search` is a PL/pgSQL function, and a connection plans each of its statements with the values of the call for the first five runs and from the sixth keeps one plan that does not know them whenever that plan's estimated cost is below the average of the five. For `@@`, `<%` and `LIKE` on a value it does not know the estimate is one row, so the estimates decide between a GIN scan and a walk of the workspace's rows through a btree (`bookmarks_owner_url_idx`, `bookmarks_slug_idx`) with the search condition as a filter, and the pages of a GIN index's pending list are added to the cost of every scan of it. The opens of `/go` reach `bookmarks` through `sys_flush_open_counts` and change columns that have indexes, so none of those updates is HOT and the entries of the five GIN indexes wait in their pending lists until a vacuum (after 30 s of the `go` scenario at 40 a second, 522 updates left 13 to 45 pages in each list, and the GIN scans of the general plan were costed at 81 to 123). The general plan then reads the 50 000 bookmarks of the workspace (`Rows Removed by Filter: 50000`) for a search that finds few bookmarks, and it serves every later search of the connection, whatever its words: a slug of a shared bookmark took 200 ms and 12 327 blocks instead of 5 ms and 381, and which connection of the pool has which plan depends on the first five searches it ran and on how many pages were pending then, which fits a p95 that moved between 0.3 and 6 s from run to run. JIT compilation was not the cause (no statement of the function is estimated above 11 000 against `jit_above_cost` of 100 000, and `jit = off` changed no timing), nor was the ranking of every title and slug match (about 4 000 rows for each of the four broad terms of the seed, 17 to 22 ms of execution and 2 800 blocks in one run each), the folder and tag statements (0.4 and 0.06 ms) or the pending lists in themselves (with 522 updates pending and every statement planned for its values, a search took 9.5 ms for `caching` and 4.6 ms for a shared slug). The plan tests did not see it: they plan the statement with the values as constants, and `blocksOfStatement` repeats one text on a vacuumed fixture. The function now plans every call for its values (`plan_cache_mode = force_custom_plan`, doc 05 §3.3), which costs the planning of the statement on each call (about 4 ms and 25 to 45 blocks, so the bounds of ten queries of `search-plan.integration.test.ts` rose by 30 to 50 blocks), and the last case of that file runs a mix of texts on one connection, on a workspace in which a tenth of the titles hold one word and the opens of `/go` have been flushed into 5 % of its rows, and holds the blocks of each call to those of the plan made for its values; without the setting a call touches 2.7 to 10 times as many (`caching` 3 316 to 5 449 blocks against 533, `docs` 3 824 against 1 174). On the large instance on PostgreSQL 18.6 (24 cores, load average 12 to 28, so the times move) the default run reported `search` at 207.6 ms (the shared slugs 228.8 ms, `do` 35.9 ms) and, with the setting, 18.4 ms (11.0 and 8.7 ms) with no arrival dropped; the highest rate with none dropped went from 80 to 320 a second (the p95 at 320 was 21.1 ms, and at 480 five arrivals were dropped).

None of the plan tests asserts a raw wall-clock time (the 100 ms above, or the 50 ms the suggestions' test once held). A time measured on a host that others share is not the time of the budget, so `search-plan.integration.test.ts` (each search), `bookmarks-list-plan.integration.test.ts` (the first page and a deep page of the list without a text in each sort, a page under each filter and the capped count), `dashboard-plan.integration.test.ts` (each statement of the dashboard), `go-suggest-plan.integration.test.ts` (the statement of `suggest` for each of 15 prefixes) and `bookmarks-list-search-plan.integration.test.ts` (below) hold the work of the plan and report the time without failing on it. A statement is run as the application role in a tenant transaction under `EXPLAIN (ANALYZE, BUFFERS)` (the helper `packages/db/test/support/plan-work.ts`) and bounded on the shared buffers it touches, `Shared Hit Blocks` plus `Shared Read Blocks`, which are the same whether a block is found in the cache or read: a statement that stops using an index it relies on, or scans the table where its plan does not, touches more and fails, except where the bound is above what the table holds (the end of this section). The bound of a statement is 5 % and 16 blocks above the most it touched in repeated runs on PostgreSQL 17 and 18, rounded up to ten, and where the two versions plan a statement differently it is the higher of the two (the sharing counts of the dashboard touch about 6 850 blocks on 17 and 9 200 to 9 230 on 18), so on the version that touches less a regression of up to the difference passes. The statement runs six times to warm up, then up to eight times, one straight after the other, until a run is under the bound, and the case fails only when none is: a plan that has regressed is over the bound in every run, while a single run can touch about 500 to 1 000 more blocks with the same plan when DDL commits elsewhere on the cluster at that moment (the extra blocks are in the scan of `sys_bookmark_match` and the planning of the same run; a reset of the backend's caches after missed invalidation messages would explain it, which is inferred and not established). The runs follow one another within milliseconds, so a retry is unlikely to meet a second commit: beside a loop of DDL transactions of 1 000 `CREATE TABLE` and of their drop, one after the other with no gap in another database (about 11 DDL commits a second), 17 of 576 first counted runs (in 12 runs of the list-with-a-text file) were over their bound and none of the 17 retries was, and no case failed in those 12 runs or in 20 others. **Heavy concurrent DDL on the cluster can still fail a case with no regression. It depends on the transaction size as well as the rate: with transactions of 1 000 tables, one loop at about 11 commits a second failed no case in 16 runs, two loops at about 28 failed one case in 7 runs, and four loops at 38 failed cases in all 5 runs; with single-table transactions, one loop at about 4 100 commits a second failed none in 5 runs, and four loops at about 12 700 failed 16 cases in each of 2 runs.** A regression that shows in only some runs of a statement passes, since a case fails only when every run is over the bound.

The time of the dashboard shows why. Through the repositories it took 34 to 57 ms at the 95th percentile in 21 runs of its file and 107 ms in one run at a load average of 32, and for one backend running it 30 times the extra time was execution, not waiting (the backend's `/proc` schedstat): 883 to 995 ms on the CPU and 0.0 to 4.1 ms in the run queue with the host quiet (3 runs), 2 139 to 2 271 ms on the CPU and 70 to 111 ms (2.6 to 4.0 %) in the run queue with the host loaded (5 runs), and 1 137 to 1 268 ms on the CPU and 0.0 to 4.7 ms in the run queue beside the integration suites of the db and server packages (6 runs, load average 13 to 21).

The slug suggestions are held the same way, with a bound for each prefix of the 15 the file tries (`s`, `-` and `docs-` among them): the statement `goRepository.suggest` runs, over `sys_go_suggest`, touches about 16 800 blocks for a prefix that matches thousands of slugs (the 5 000 grants of the caller are probed by primary key for the shared candidates), 972 to 980 for `slug-1`, 324 to 332 for `slug-12` and 160 to 180 for `gh`, `zz` and `a`, and the bound is 5 % and 16 blocks above the most it touched in the runs on PostgreSQL 18 (4 runs, and for `slug-1` and `slug-12` the freshly seeded fixtures of repeated runs, whose random identifiers move the two together), rounded up to ten (17 680 to 17 700 for the large ones, 1 050 for `slug-1`, 370 for `slug-12` and 200 to 280 for the others). The blocks were the same within 2 on PostgreSQL 17 and 18 and on a CPU-limited database and a free one before the setting below (the most of 11 runs: 4 on each version under `--cpus 0.3` and 3 on 18 without a limit); they were not measured on 17 again. With `bookmarks_slug_trgm_idx` dropped, 6 of the 15 per-prefix cases fail (`slug-1`, `slug-12`, `gh`, `zz`, `a` and `9`) and so do the 9 plan cases of the file (2 runs on PostgreSQL 18, a load average of 42 to 49; not measured on 17): a prefix touches 16 827 to 16 868 blocks, 16 to 84 times the bound of a prefix that matches few slugs, but only 812 to 872 blocks under the bound of one that matches thousands, so the nine large prefixes pass and the small prefixes and the plan cases of the file, which name the index, are what catch the drop (with the index the large ones touch 16 818 to 16 833). The file reports the 95th percentile of the 150 answers and does not fail on it: 9.8 to 11.5 ms on a free database (3 runs, load average 8) and 69.5 to 72.1 ms with the database limited to 0.3 CPU (6 runs; the former assertion of 50 ms failed at 71.3 ms in another run there with the plan unchanged).

**The plan the suggestions keep.** `sys_go_suggest` is a PL/pgSQL function, and a connection plans its statement with the values of the call for the first five runs and from the sixth keeps one plan that does not know them whenever that plan's estimated cost is below the average of the five, which is the mechanism that hurt `sys_search` above. The measurement of `sys_go_suggest` on this file's fixture, after the opens of `/go` had been flushed into a tenth of the slugged bookmarks (non-HOT updates after a vacuum, so the entries of the GIN indexes wait in their pending lists), taking the first call of the connection as call 1: calls 1 to 5 (`zzz`, `s`, `d`, `m`, `g`) used plans made for their values, and from call 6 the general plan read 3 600 to 3 800 blocks for every prefix (3 625 to 3 630 for `gh`, `zz`, `a` and `9` against 226 to 316 for the plan made for the value, 11 to 16 times as many) and took 46 to 103 ms for the prefixes that match thousands of slugs (`s`, `d`, `g`, `docs-`, `mail`) against 10 to 14 ms. The pages of a GIN pending list are added to the cost of every scan of the index, so the scan of `bookmarks_slug_trgm_idx` was costed at 160 or more and the walk of `bookmarks_owner_slug_key` and `bookmarks_slug_idx` with the prefix as a filter at about 5; the general plan chose the walk, tested each of the grants against each shared candidate (1.6 million rows removed by the join filter for `docs-`), and served every later prefix of the connection. After a vacuum the general plan was the trigram scan again (3 200 to 3 300 blocks and 4 to 5 ms for the broad prefixes, 130 to 220 blocks for the narrow). The function therefore plans every call for its values (`plan_cache_mode = force_custom_plan`, doc 05 §3.3): the narrow prefixes read 160 to 400 blocks whatever the lists hold, and the broad ones about 16 800 blocks at 9 to 14 ms in place of 3 400 at 4 ms on a vacuumed table, which is inside the 50 ms and does not depend on the connection or on its pending lists. ### 5.4 Migration timing

The scheduled workflow (`nightly.yml`, job `migration timing`) applies the pending migrations to the large instance with `migrate` and reports each migration's duration and its longest `ACCESS EXCLUSIVE` lock; a migration that holds that lock for more than 1 s fails the job (doc 05 §5.2). `scripts/perf/migrations.mjs` is the entry point (`pnpm perf:migrations` locally, against the development Postgres of `compose.dev.yml`); neither is part of `pnpm gate`.

- **Baseline.** The schema is built at the migration level of the latest release tag, read from git the way `pnpm db:check` reads it (`readReleaseState`), so the run measures exactly the migrations a release adds. The large instance (§5.3) must be written at that level: when a table, a column or a system operation that the seed script writes through is missing there, the baseline is raised, one migration at a time, to the first level at which none is missing. What the seed needs is read from the seed script itself and checked with a query against the catalog before any row is written, so the baseline cannot need less than the seed does. Today the latest release, `v0.1.0`, has no `bookmarks` table, so the baseline is the first level that has all of the instance's tables, and every migration after it is measured; from the first release that holds the tables on, it is the release's own level. The report names the release, its level, what that level lacked and the baseline used. The per-release data snapshot (1.0.0) can replace this construction once it exists.
- **Database.** One that the test harness names (`test_` and 16 hex digits), created for the run on a loopback server or the one `SLUGBASE_TEST_PG_URL` names, and dropped when the run ends however it ends. The schema is built with `migrate`, and nothing uses `drizzle-kit push`.
- **Applying.** Each migration of the CE chain after the baseline is applied by its own `migrate` call, stopped after it with the `until` option, so the call runs under the advisory lock with the `lock_timeout` and `statement_timeout` of the `migrate` command (doc 05 §5.3) and applies exactly that migration; a call that applies anything else fails the run.
- **Report.** `result.json` and the job summary give, per migration file, the wall time of the call, the longest `ACCESS EXCLUSIVE` lock held and the relation it was on, and whether the file is non-transactional. A sampler polls `pg_locks` every 50 ms for an `ACCESS EXCLUSIVE` lock held by the `slugbase-migrate` backend on a relation of a user schema, on the server's clock; the time of a lock is the longest run of polls that saw it, so it is short of the real time by less than two polls. A sampler that cannot see other sessions, that fails or that ends early fails the run. The report states that backfills are worker jobs and are not part of a migration, and that a non-transactional step (a concurrent index build, doc 05 §5.2) takes no `ACCESS EXCLUSIVE` lock on the table it indexes, so it is reported with its duration only and is not judged.
- **Failure.** A migration whose lock was held for more than 1 s fails the run (exit status 10) and the failure names the migration file and the relation; a run interrupted by `SIGINT`, `SIGTERM` or `SIGHUP` drops its database and exits with `128 + n`, `n` being the number of the signal; any other failure of the run exits 1. `packages/testing/test/migration-timing.integration.test.ts` reproduces it: after the CE chain, a fixture chain (`packages/testing/test/fixtures/long-lock/`, never in the real chain) rewrites a table of 50 000 rows under `ACCESS EXCLUSIVE` and holds the lock for 1.5 s, which fails, and a fixture that adds a nullable column passes. A migration that fails the check is changed in an item of its own.

## 6. CI

### 6.1 Runners

| Repository | Runner | Why |
|---|---|---|
| `mdg-labs/slugbase` (public) | GitHub-hosted `ubuntu-latest` | Free for public repos; nothing private to protect (`githubRunner`, doc 09 §5.2) |
| Private repositories | Self-hosted CI runners | Described in the Cloud documentation |

Workflows in this repository use a portable shape where it costs nothing: every `ci.yml` job except `build`, `image-scan` and `integration-pooled` runs in a container (`container: node:24-bookworm`), installs pnpm with `pnpm/action-setup`, and reaches service containers **by name** (`postgres:5432`), never `localhost`; image builds use plain `docker build`/`docker push`. `build` runs on the runner itself, because its image smoke test (`scripts/smoke-image.sh`) starts the image with Docker Compose and needs the runner's own Docker daemon and published ports; it takes Node from `actions/setup-node` at the major version of `.nvmrc` and uses the same `setup` action as the others. `integration-pooled` runs on the runner as well, because it starts the Postgres and the PgBouncer of `compose.dev.yml` with the runner's Docker daemon; it takes Node from `actions/setup-node` like `build`. `image-scan` runs on the runner as well, because it builds the image with `docker buildx build` on a `docker-container` builder to get BuildKit's SPDX SBOM, which needs the runner's own Docker daemon; it sets up neither Node nor pnpm, and downloads the pinned OSV-Scanner with `scripts/scan-image.sh --install`, which checks it against a pinned checksum. The other `ci.yml` jobs can therefore move to ephemeral self-hosted CI runners unchanged, and `build`, `integration-pooled` and `image-scan` can too on a runner that has a Docker daemon of its own (and, for `build` and `integration-pooled`, the Docker CLI with the Compose plugin; for `image-scan`, buildx).

`e2e.yml` is a runner job for the same reason: its stack (`e2e/with-stack.sh`, through `scripts/smoke-image.sh`) runs on the runner's own Docker daemon with its ports published on `127.0.0.1`. Only the journeys run in a container, the official Playwright image of `e2e/Dockerfile` (`e2e/in-image.sh`: the repository mounted at its own path, the host's network, the user of the runner so that `e2e/test-results/` and `e2e/playwright-report/` stay readable by the upload step, the `E2E_*` variables handed on by name). The image carries the three engines and their system libraries, so no step installs them from a package mirror, whose speed once decided the job's time. Its tag is the version of `@playwright/test` that `pnpm-lock.yaml` resolves and its digest pins it; `renovate.json` updates both in one group and `e2e/support/playwright-image.test.ts` fails when they differ. The journeys import workspace packages (`@slugbase/testing` for their fixtures) whose `exports` point at `dist/`, so the job builds `@slugbase/e2e`'s dependencies (`pnpm turbo run build --filter='@slugbase/e2e^...'`) on the runner before the journeys; the mounted checkout carries the output into the container, and `e2e/support/playwright-image.test.ts` fails when the step is missing or comes after the journeys.

The jobs of `e2e.yml` are `shards` (a matrix over the PostgreSQL major and the shard, named `e2e shard (PostgreSQL <n>, <i>/4)`: build, pull, journeys, leftover-stack removal, and on failure an upload named `e2e-artifacts-postgres-<n>-shard-<i>`, so two shards never overwrite each other) `restore-drill` (a matrix over the PostgreSQL major, named `restore drill (PostgreSQL <n>)`: build the image, run `pnpm --filter @slugbase/e2e test:e2e restore-drill`, leftover-stack removal, and on failure an upload named `restore-drill-artifacts-postgres-<n>`) and `e2e`, a summary job that keeps the names `e2e (PostgreSQL 17)` and `e2e (PostgreSQL 18)` that the ruleset of `main` requires. `restore-drill` runs the backup and restore drill of `docs/self-hosting/backup-restore.md` (`e2e/restore-drill.spec.ts`, configured by `e2e/restore-drill.config.ts`, §5.1) once per PostgreSQL major, on the image built from the commit, so the guide's commands are proved against the database of each major the images support. It is a job of its own because it dumps, destroys and restores the database of a stack that is its own (`e2e/restore-drill-stack.sh`) and so cannot share one with the shards, and because it needs docker, which the Playwright image does not have: it runs on the runner and needs no browser and pulls no Playwright image. The summary runs whatever the shards and the drill did and fails unless the whole `shards` matrix and the whole `restore-drill` matrix succeeded; a failed, cancelled or skipped shard or drill is never a pass. Because `needs` waits for both whole matrices, a failing shard or drill fails both required checks, and the failing job names the leg that failed.

### 6.3 Workflows — Cloud

(Cloud) Recorded in the Cloud documentation. In outline: CI on every push, Cloud e2e journeys, and a deploy workflow that runs `migrate` as a separate step before rolling out new containers (D25).

### 6.4 The gate, per repository

`pnpm gate` is defined in each root `package.json` and is exactly what `workflow.json` `gate` runs (doc 09 §5.2):

- **CE**: `pnpm lint` (including the forbidden-terms check) → `turbo run typecheck test:unit build` → `pnpm contracts:check` → `pnpm db:check` → `pnpm test:integration` → `pnpm i18n:check` → `pnpm audit --audit-level=high`.
- **Cloud**: the CE pin check, then the same sequence over the Cloud workspace, plus its own checks (Cloud documentation).

The documentation contract check `pnpm docs:check` (doc 09 §3.5) is a per-path check for changes under `docs/user/`, `docs/self-hosting/` and `docs/releases/`, and runs as the `docs` job of `ci.yml`; it is not part of `pnpm gate`. Per-path `checks` (the faster subset an executor runs before each commit) are listed in doc 09 §5.2. e2e is **not** in the gate — it needs a built image and a minute or two of browser time; it runs in CI and before promotions, and an executor runs the relevant spec only when an item's acceptance criteria name an e2e journey.

### 6.5 Merge and promotion gate

`dev` takes cherry-picked commits from `/orchestrate` only after the verifier has re-run the gate; CI on `dev` re-runs it plus e2e. The `dev → main` promotion PR needs green CI, green e2e, one CodeRabbit round (`/pr-review`), a clean `/security-audit` for the changed security units (D23) and the maintainer's merge. `main` is protected: no direct pushes and no force pushes. The promotion PR is merged with a merge commit, so the tree on `main` is the tree that was reviewed on `dev` (Cloud doc 13 Q78 relies on that identity). Linear history is therefore not required on `main`.

## 8. Development loop, in practice

```bash
pnpm dev:services && pnpm dev                 # once per session
pnpm test:unit --filter=@slugbase/core        # tight loop on domain logic
pnpm test:integration --filter=@slugbase/db   # RLS / repository work
pnpm dev:web --mock                           # UI work without the server
pnpm gate                                     # before every commit an agent makes
pnpm test:e2e -- --grep "go disambiguation"   # when an item names a journey
```

The executor in a scratch clone runs `bootstrap` (`pnpm install --frozen-lockfile`, plus `git submodule update --init` in Cloud), then the `checks` for the paths it touched, then `pnpm gate`; the verifier runs `pnpm gate` itself in its own clone. Both use the shared development Postgres through the per-test database harness (§3.2) and never touch `slugbase_dev`'s data.
