# SlugBase — Data Model

PostgreSQL is the only database (D6): 17 and 18 are supported (Q3), 18 is the version the compose file ships. The Drizzle schema in TypeScript is the single source; migrations are generated from it (D7). This document is the reviewed design that schema implements: every table, its constraints, indexes and row-level-security policy, the database roles, the few system operations that cross tenants, the migration policy and data lifecycle.

---

## 1. Conventions

| Rule | Value |
|---|---|
| Primary keys | `id uuid` holding a UUIDv7 generated in the application (Q91) — no database default, so PostgreSQL 17 and 18 behave the same and tests can inject a sequence; association tables use composite natural keys |
| Tenant column | `workspace_id uuid NOT NULL` on every tenant-owned table, first column of every composite key and of every index whose queries are workspace-scoped |
| Intra-workspace references | **Composite foreign keys** `(workspace_id, x_id) REFERENCES x (workspace_id, id)` — each referenced table has `UNIQUE (workspace_id, id)`. A row can therefore never point at a row in another workspace, even if application code passes a foreign ID (defence alongside RLS, D8) |
| Timestamps | `timestamptz NOT NULL DEFAULT now()`; `created_at`, `updated_at` on editable tables, where `updated_at` is maintained by the trigger function `public.set_updated_at()` (declared once in `packages/db/src/sql/090-updated-at-trigger.sql`), which each such table attaches as a `BEFORE UPDATE` row trigger named `<table>_set_updated_at` in `packages/db/src/sql/`; nullable `*_at` columns for state (`verified_at`, `revoked_at`, `plan_archived_at`, `deleting_at`) instead of booleans plus a timestamp |
| Optimistic concurrency | `version integer NOT NULL DEFAULT 1`, incremented by the update trigger on folders and teams, by the `bookmarks_bump_version` trigger on bookmarks (§2.4) and by the rename statement itself on workspaces (API `ETag`/`If-Match`, doc 04 §2.4). A workspace's `bookmark_count` and `entitlement_version` change without moving it, so a bookmark write does not stale a workspace's `ETag` |
| Case-insensitive text | `citext` for emails, slugs and names compared case-insensitively |
| Enums | Postgres enum types (`member_role`, `share_target`, …); adding a value is an expand-only migration (§5.4) |
| Secrets | Never stored in plaintext: tokens as `bytea` SHA-256 hashes; MFA secret as `bytea` ciphertext + `key_id` via `SecretBoxPort` |
| Naming | `snake_case` tables (plural) and columns; indexes `<table>_<cols>_idx`, uniques `<table>_<cols>_key`, policies `<table>_tenant` |
| Deletion | Hard delete with FK `ON DELETE CASCADE` along ownership; no soft delete in v1 (doc 00 §4). The one transient state is a workspace marked `deleting` while its background job runs (§7.2) |

### Extensions

`citext`, `pg_trgm`, `btree_gin` (multi-column GIN with `workspace_id`). Created by the first migration as the owner role. Nothing that needs superuser at runtime.

### Schemas

| Schema | Owner of the migration history | Contents |
|---|---|---|
| `public` | CE (`mdg-labs/slugbase`) | Everything in §2 |
| `pgboss` | pg-boss (installed and upgraded by `migrate` with the library's own plans, §5.5) | Job queue |
| `cloud` | The private Cloud repository | Cloud-only records (§2.12, Cloud doc 06) |
| `console` | The private Cloud repository (operator console) | Operator accounts, sessions, audit, daily snapshots (Cloud doc 07 §6) |
| `drizzle` | each chain | Migration bookkeeping, one table per chain: `drizzle.migrations_core`, `…_cloud`, `…_console`; and `drizzle.pgboss_pending_builds`, the record of the pg-boss index builds an upgrade still owes (§5.5; owner-only) |

Billing data does **not** live in SlugBase's database: customers, payments and billing documents stay in the external billing service (D29). The `cloud` schema holds only the billing state the Cloud entitlement source needs.

## 2. Tables (`public`)

RLS column: **T** = tenant policy (`workspace_id = app_workspace_id()`), **A** = account policy (`account_id = app_account_id()`), **T+A** as stated, **S** = system-only (no app policy; reached through §3 functions only), **—** = no RLS (no tenant or personal data). Every table with RLS has both `ENABLE` and `FORCE ROW LEVEL SECURITY`.

`app_workspace_id()` and `app_account_id()` are `STABLE` SQL functions returning `nullif(current_setting('app.workspace_id', true), '')::uuid` (and the account equivalent) — NULL when unset, so a query outside `withTenant` matches nothing.

Policies: `accounts_tenant`, for every command, `USING (id = app_account_id())` with `WITH CHECK (id = app_account_id())`, and `accounts_tenant_co_members`, for `SELECT` only, `USING (id IN (SELECT account_id FROM workspace_members WHERE workspace_id = app_workspace_id()))`; permissive policies add up, so a read shows the own row and the rows of the active workspace's members, and a write reaches the own row only. Co-members see the row, but the repository's co-member projection (`memberRepository`) selects only `id, display_name, email` — sensitive columns are additionally protected by **column privileges**: `slugbase_app` has no `SELECT` on `password_hash`, `mfa_secret`, `mfa_secret_key_id`, `mfa_last_step`; those are read and written only through §3 functions. `slugbase_app` is granted `SELECT` on the other columns only, and `INSERT`, `UPDATE` and `DELETE` with the operations that need them.

**`oidc_login_states`** — RLS: S

`state_hash bytea PK` (SHA-256 of the `state` value), `provider text`, `intent text` (`login` / `link` / `reauth` / `invite`), `nonce text`, `code_verifier bytea` (SecretBox) with `code_verifier_key_id text` (the key that sealed it), `return_to text` (validated same-origin path), `link_account_id uuid NULL` (the signed-in account for the `link` and `reauth` intents), `invitation_token_hash bytea NULL` (SHA-256 of the token of the invitation to accept, set exactly for the `invite` intent: the token itself is never stored, and an `invite` record's `return_to` is always `/`, so the token reaches no column), `expires_at timestamptz` (10 min). Deleted on use, which uses the token hash up with it.

**`api_tokens`** — RLS: A for management, lookup is S

| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | |
| `account_id` | uuid NOT NULL | |
| `workspace_id` | uuid NOT NULL | Bound workspace, chosen at creation among the account's workspaces (doc 04 §4.2) |
| — | FK `(workspace_id, account_id)` → `workspace_members` ON DELETE CASCADE | Losing membership deletes the token |
| `name` | text NOT NULL | 1–64 chars |
| `token_hash` | bytea NOT NULL UNIQUE | SHA-256 (32 bytes) of the whole token as the bearer presents it (`slb_` + 32 random bytes as 43 base64url characters); `slugbase_app` has no SELECT on the column |
| `token_prefix` | text NOT NULL | First 6 chars after `slb_`, for display and leak scanning |
| `scope` | text NOT NULL | `read` / `read-write` |
| `expires_at` | timestamptz | NULL = no expiry (Q47); the creation dialog defaults to 90 days |
| `last_used_at` | timestamptz | Written at most once a minute |
| `last_used_ip_prefix` | cidr | Same coarse prefix as sessions, written with `last_used_at` |
| `revoked_at` | timestamptz | Set by `DELETE /me/api-tokens/{id}`, keeping the first time; the row stays, so a repeated revocation is answered as the first one (doc 04 §2.4), and the token lookup treats it as inert |
| `created_at` | timestamptz | |

Unique `(account_id, name)` among the rows with `revoked_at IS NULL` (a partial unique index), so a revoked token's name can be used again; CHECKs on the name length, the hash length (32), the prefix length (6) and the scope. The per-account count (10 tokens that are neither revoked nor expired, `MAX_API_TOKENS_PER_USER`) is enforced in the service, under a lock on the account's row so two creations at once cannot both pass it. Management uses the account policy `account_id = app_account_id()` in an account-level transaction; `slugbase_app` may read every column but `token_hash`, insert and update `revoked_at` alone, and holds no DELETE (a token leaves with its membership or account, or when `sys_retention_purge()` deletes it 30 days after it was revoked or expired, §6).

**`mfa_backup_codes`** — RLS: S (enabled and forced, no policy; `slugbase_app` has no privilege on it). `id`, `account_id` → accounts CASCADE, `code_hash bytea` (the argon2id PHC string, as bytes, of the 10-char code — low entropy, so a slow hash), `used_at`. Partial index `(account_id) WHERE used_at IS NULL`.

**`credential_tokens`** — RLS: S. One table for every emailed single-use token.

| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | |
| `purpose` | text NOT NULL | `email_verify` / `email_change` (the confirmation link to the new address, redeemed by `POST /me/email/confirm`) / `email_change_cancel` (the "this wasn't me" link to the old address, redeemed by `POST /me/email/cancel`) / `password_reset` |
| `account_id` | uuid NOT NULL → accounts CASCADE | |
| `token_hash` | bytea NOT NULL UNIQUE | |
| `target_email` | citext | For `email_change`: the address it moves the account to; for `email_change_cancel`: the address the account holds when the token is issued, which the link puts back after the change was confirmed; null for the other purposes |
| `expires_at` | timestamptz NOT NULL | 1 hour (verify: 24 hours, Q48) |
| `used_at` | timestamptz | |
| `created_at` | timestamptz | |

Issuing a new token of a purpose invalidates (deletes) older unused ones for the same account. The one exception is `email_change_cancel`: issuing one deletes only the unused cancel tokens that target the account's current address (or no address), so the undo link of a confirmed change stays (`sys_email_change_token_issue`). While a cancel token is unused and unexpired, its `target_email` is reserved to its account: `sys_create_account` and `sys_email_change_confirm` treat it as an address another account holds, so the owner's restore cannot be pre-empted. The lookup reads `credential_tokens` without an index on `target_email`; the table holds only live tokens and those used or expired within the last 7 days. A cancel token's `created_at` is set from the clock at that insert, under the account's row lock, so the cancel tokens of an account are ordered like the addresses they record; redeeming one deletes the account's unused cancel tokens created after it (`sys_email_change_cancel`).

### 2.2 Workspaces and membership

**`workspaces`** — RLS: rows the account is a member of; writes only on the active workspace

| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | |
| `name` | text NOT NULL | 1–64 chars |
| `created_by` | uuid → accounts ON DELETE SET NULL | |
| `entitlement_version` | integer NOT NULL DEFAULT 1 | Bumped on any plan, archive-state or override change (cache key, doc 01 §7.5 and §8.3). `slugbase_app` has no privilege on the column; the change raises it by one through `sys_workspace_bump_entitlement_version` (§3.3) in the transaction that makes the change (`withEntitlementChange` in `@slugbase/core`). The bump moves neither `version` (the `ETag`) nor `name`; `updated_at` moves, as on every `UPDATE` |
| `bookmark_count` | integer NOT NULL DEFAULT 0 | Number of the workspace's bookmarks that are not plan-archived. Maintained in the same transaction as every bookmark create, delete, import, archive and restore; the entitlement check reads it under the workspace row lock instead of counting rows (doc 01 §7.5). A create raises it through `sys_bookmark_count_take`, a delete lowers it through `sys_bookmark_delete` and a bulk delete through `sys_bookmark_delete_many` and an archive or a restore moves it through `sys_bookmark_archive_set` (§3.3), which `slugbase_app` calls because it has no `UPDATE` privilege on the column |
| `deleting_at` | timestamptz | Set when deletion is requested (§7.2); the workspace is then hidden from every product query, the switcher and `GET /workspaces` |
| `version` | integer NOT NULL DEFAULT 1 | |
| `created_at`, `updated_at` | timestamptz | |

Policy: `USING ((id = app_workspace_id() OR id IN (SELECT app_member_workspace_ids())) AND deleting_at IS NULL)` for `SELECT` (`workspaces_tenant`); `id = app_workspace_id()` for `UPDATE`/`DELETE` (`workspaces_tenant_update`, `_delete`), so the deletion job can finish. `app_member_workspace_ids()` is a `SECURITY DEFINER` set-returning function owned by `slugbase_system` that returns the calling account's workspace IDs (the account is `app_account_id()`, never an argument) from `workspace_members`, leaving out workspaces being deleted (avoids recursive policy evaluation). `slugbase_app` may `SELECT` the table and `UPDATE` its `name` and `version` columns and no other (a column grant, so a statement naming `deleting_at`, `bookmark_count` or the identifier is refused by privilege); the rename locks the row (`SELECT … FOR UPDATE`), compares `version` with the caller's `If-Match` under the lock and writes `name` and `version = version + 1` in one transaction with its `workspace.renamed` audit event. Whether the caller may rename is the role check of the authorization stage; the policy names the active workspace only, so a transaction acting in A neither locks nor changes B. The operations that delete a workspace grant what they need. `updated_at` is maintained by the `workspaces_set_updated_at` trigger (§1). Insert happens through `sys_create_workspace` (§3), which also inserts the owner membership atomically.

No billing columns: in Cloud, billing state lives in the `cloud` schema (§2.12, Cloud doc 06); CE has none (D18). `entitlement_version` and `bookmark_count` are generic and exist on every edition.

**`workspace_members`** — RLS: T, plus the account's own rows

| Column | Type | Notes |
|---|---|---|
| `workspace_id` | uuid NOT NULL → workspaces ON DELETE CASCADE | |
| `account_id` | uuid NOT NULL → accounts ON DELETE CASCADE | |
| `role` | `member_role` NOT NULL | `owner` / `admin` / `member` |
| `joined_at` | timestamptz | |
| `last_active_at` | timestamptz | NULL = never active. Written at most once a minute by the tenant resolver, for a session request in the workspace it resolved; shown as "last active" in the members list and orders the re-derivation of the active workspace: most recently active first (never active last), then newest `joined_at`, then `workspace_id` |

PK `(workspace_id, account_id)`; index `(account_id)`. **At least one owner** per workspace: a deferred constraint trigger (`workspace_members_owner_required`, `AFTER DELETE OR UPDATE`, `DEFERRABLE INITIALLY DEFERRED`, `FOR EACH ROW`, function `workspace_members_check_owner()`) checks when the transaction commits, for every deleted or updated row that was an owner in its workspace and is not one there afterwards, that the workspace still has an owner, unless the workspace itself is being deleted (`deleting_at` set, or the row gone in the same transaction) (a workspace created for an owner invitation has no member until it is accepted; the trigger does not fire for an insert). A violation is a `check_violation` (SQLSTATE `23514`) naming the constraint `workspace_members_owner_required`, which the API answers `409 last_owner`. Two transactions that each remove a different owner cannot see each other's change, so the function first takes `FOR NO KEY UPDATE` on the workspace's row, which queues the second transaction until the first has committed, and counts the owners in a statement of its own that reads the committed state (the function is `VOLATILE` and the transaction `READ COMMITTED`): exactly one of two owners demoting each other at the same moment commits. The function is `SECURITY DEFINER` as `slugbase_system` (listed in §3.3), so it counts every member whatever the caller's policy shows. A constraint trigger has no `CREATE OR REPLACE`, so the declarative SQL drops it (`DROP TRIGGER IF EXISTS`) and creates it again in the same migration. Policies: `SELECT` `USING (workspace_id = app_workspace_id() OR account_id = app_account_id())` (`workspace_members_tenant`); `UPDATE` and `DELETE` only `USING (workspace_id = app_workspace_id())` (`workspace_members_tenant_update`, `_delete`), so writes happen only in the active workspace, and there is no `INSERT` policy: a membership is added by a system operation. `slugbase_app` may `SELECT` the table and `UPDATE (role, last_active_at)`: a role change is a row update in the active workspace, and who may make it is the member service's check (doc 02 §3.3), not the policy's; the membership changes that remain grant what they need.

**`workspace_invitations`** — RLS: T (inspect/accept by token is S)

| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | |
| `workspace_id` | uuid NOT NULL | |
| `email` | citext NOT NULL | |
| `role` | `member_role` NOT NULL | CHECK `role <> 'owner' OR instance_issued`: the public operations never create an owner invitation |
| `instance_issued` | boolean NOT NULL DEFAULT false | True only for an owner invitation, which `sys_instance_create_workspace` writes for a workspace created without an owner account and `sys_instance_reissue_owner_invitation` writes for a workspace that still has no owner, ending the pending ones (`invited_by` the instance admin; the mail ticket is the invitation's own identifier, the ticket of the `invitation.send` job queued with it where mail is configured, and the token is either the one that job makes or one whose value the admin is given once as a link); `slugbase_app` has no `INSERT` privilege on this column, so `POST /invitations` can neither set it nor write an owner |
| `team_ids` | uuid[] NOT NULL DEFAULT `'{}'` | Teams to join on accept; validated on invite and again on accept (deleted teams are skipped) |
| `token_hash` | bytea NOT NULL UNIQUE | SHA-256 of the token, 32 bytes. Regenerated on resend/link. The request that writes or resends an invitation stores the hash of a token nobody has, which ends the earlier link at once (except where the composition cannot send mail: there a request that resends a pending invitation keeps the stored hash, so a link copied from the link operation keeps working); the job that emails the link replaces it with the hash of the token it sends, so the token is in no request, queued payload or log. The one exception is the link operation (doc 04 §10.5): its request makes a token, stores the hash and returns the token once in its response, which ends the earlier link as well |
| `mail_ticket` | uuid | The identifier (no secret) of the mail job queued by the request that last wrote or resent the invitation; NULL when a link replaced it or the invitation was seeded. The job carries it in its payload and replaces `token_hash` only where the row still holds it, so a link copied after the job was queued, or a later resend, is not ended by that job; a retry of the same job finds its ticket still on the row and issues a token again |
| `invited_by` | uuid → accounts ON DELETE SET NULL | |
| `status` | text NOT NULL | `pending` / `accepted` / `revoked` |
| `expires_at` | timestamptz NOT NULL | 7 days |
| `accepted_by` | uuid → accounts ON DELETE SET NULL | |
| `closed_at` | timestamptz | When `status` left `pending`: set by the statement that revokes or accepts the invitation and by nothing else, so a later change to the row (an inviter's or accepter's account deleted, which nulls the column) does not move it. NULL exactly while the invitation is pending (CHECK `workspace_invitations_closed_at_check`). The retention purge counts its 30 days from it |
| `created_at`, `updated_at` | timestamptz | |

Partial unique `(workspace_id, email) WHERE status = 'pending'`. Expiry is evaluated at read time; the purge job deletes non-pending rows 30 days after `closed_at`. `slugbase_app` may `SELECT` the table, `INSERT` the columns `id`, `workspace_id`, `email`, `role`, `team_ids`, `token_hash`, `mail_ticket`, `invited_by` and `expires_at` (so a row it writes is pending, never accepted and never instance-issued) and `UPDATE` the columns a resend or a link replaces (`role`, `team_ids`, `token_hash`, `mail_ticket`, `invited_by`, `expires_at`) and `status` with `closed_at`, under policies that name the active workspace (`workspace_invitations_tenant`, `workspace_invitations_tenant_insert`, `workspace_invitations_tenant_update`); the update policy admits only a row that is `pending` and leaves it `pending` or `revoked`, so the application role revokes a pending invitation and can neither accept one nor reopen a revoked one (accepting is a system operation); it never deletes a row. `expires_at` is set from the database clock when the row is written (`now()` plus the invitation lifetime). The table is in the workspace purge registry (§7.2).

**`workspace_settings`** — RLS: T. One row per workspace, typed columns (no key/value table): `workspace_id` PK → workspaces CASCADE, `ai_enabled boolean NOT NULL DEFAULT true`, `updated_at`, `updated_by`. New settings are new columns. `slugbase_app` may `SELECT` the table and `UPDATE` the setting columns and `updated_by` only, under an `UPDATE` policy that names the active workspace (`workspace_settings_tenant_update`); the row is written by `sys_create_workspace`, so it is never inserted or deleted by the application role. A settings change locks the row, so the old value an audit event records is the value the change replaced.

**`instance_state`** — RLS: — (no personal data). Single row (`id smallint PK CHECK (id = 1)`): `setup_completed_at timestamptz`, `setup_by uuid`, `setup_token_hash bytea` (SHA-256 of the setup token the server generates at each start while no account exists and prints to its log; a start replaces the hash, so only the latest token works; the token itself is never stored). Written only by `sys_setup_token_set` and `sys_complete_setup`.

**`instance_settings`** — RLS: — (no personal data; the display name and the sign-in notice are public on the sign-in page). A name is created with `INSERT … ON CONFLICT (workspace_id, owner_id, name) DO NOTHING` and renamed by an `UPDATE` that requires that no other tag of the owner has the name, so a name that is taken is an answer (`409 name_taken`) and two creations of one name at the same time make one tag; two renames to one name that overlap can still meet at the unique key, and the loser ends its transaction with nothing written and the same answer. The table is in the workspace purge registry (§7.2).

**`bookmark_tags`** — RLS: T + tag owner (same predicate via the tag): `USING (workspace_id = app_workspace_id() AND EXISTS (SELECT 1 FROM tags t WHERE t.workspace_id = bookmark_tags.workspace_id AND t.id = bookmark_tags.tag_id AND t.owner_id = app_account_id()))` (`bookmark_tags_tenant`, `SELECT`). `workspace_id`, `bookmark_id`, `tag_id`; PK `(bookmark_id, tag_id)`; composite FKs `(workspace_id, bookmark_id)` to `bookmarks` and `(workspace_id, tag_id)` to `tags`, both CASCADE (so a link never joins a bookmark and a tag of different workspaces, and deleting either deletes its links); index `(workspace_id, tag_id)`. The count of a tag (`bookmarkCount` of `GET /tags`) is the number of its links to bookmarks that are not plan-archived. The table is in the workspace purge registry (§7.2).

### 2.10 Infrastructure tables

**`idempotency_keys`** — RLS: A. `account_id`, `key uuid`, `operation text`, `request_hash bytea`, `status` (`in_progress` / `done`), `response_status`, `response_body jsonb`, `created_at`, `expires_at` (24 h). PK `(account_id, key)`. `request_hash` is the SHA-256 of the operation, workspace and validated request (doc 04 §6.3). The row is inserted `in_progress` and completed `done` with the response inside the transaction that runs the request, so no committed row stays `in_progress` and a concurrent duplicate waits on the unique index until that transaction ends; a rollback leaves no row. A claim in a workspace transaction first locks the workspace's row `FOR KEY SHARE`, before it inserts the key and before it lowers `lock_timeout` for the wait on the key, so a wait on that row is not reported as a key still running. The insert takes `FOR KEY SHARE` on the account's row through the foreign key, and the deletion of an account locks the workspaces before the account (§7.1); a claim that held the account first and met the workspace in the request's writes would deadlock with that deletion. `FOR KEY SHARE` is the weakest lock that the deletion's `FOR UPDATE` conflicts with, and it does not conflict with the `FOR NO KEY UPDATE` of `sys_bookmark_count_take` (§3.3), so creations in one workspace do not queue on each other. A claim in an account-level transaction takes no workspace lock. `response_status` is a `2xx` status, and `slugbase_app` can insert and update but not delete a key (`sys_retention_purge` does, once `expires_at` has passed).

**`rate_limit_buckets`** — `UNLOGGED` (defined in `packages/db/src/sql/`, because the Drizzle schema cannot express it), RLS: S. `key text PK` (bucket + IP/principal hash), `tokens real`, `updated_at timestamptz`. Lost on crash or failover by design — limits reset, nothing else breaks (doc 10 §5).

**`pgboss.*`** — owned by pg-boss. Job payloads carry IDs, never secrets or full documents; the worker re-reads current state. The one exception is the "new sign-in" `mail.send` job, which also carries the time of the sign-in, the browser family and the coarse network prefix (none is a secret; never a full address, a user agent or a token): the alert was decided while the account's switch was on, so it is sent whatever becomes of the session or the switch before the worker runs or between attempts.

### 3.1 Roles

`slugbase_owner` is a member of `slugbase_system` (`WITH INHERIT TRUE, SET TRUE`): a migration creates a §3.3 function as the owner and runs `ALTER FUNCTION … OWNER TO slugbase_system`, granting `CREATE` on the schema to `slugbase_system` only for the length of that statement block. `slugbase_system` holds no privilege the owner lacks, and `BYPASSRLS` is a role attribute that membership does not pass on, so the owner does not bypass row-level security. An existing install and a managed provisioning need the same grant. Server and worker both connect as `slugbase_app` (worker pool distinct, same role). In CE, the compose file provisions `slugbase_app` and `slugbase_migrator` through a Postgres init script (`packages/db/provision/roles.sql`, idempotent, passwords supplied as variables) and passes two URLs (`DATABASE_URL`, `DATABASE_MIGRATE_URL`). With only `DATABASE_URL` set and that role owning the database, the server refuses to start in production; `SLUGBASE_ALLOW_OWNER_CONNECTION=true` overrides it, with a warning (Q56).

Exclusions for `slugbase_app`: no column `SELECT` on `accounts.password_hash`, `mfa_*`; no table access to `sessions`, `oidc_login_states`, `mfa_backup_codes`, `credential_tokens`, `favicons`, `rate_limit_buckets`, `instance_state` except through functions; `SELECT` only on `instance_settings`; `INSERT`/`SELECT` only on `audit_events`; no `INSERT` on `workspace_invitations.instance_issued`.

### 3.2 The tenant transaction

`withTenant(ctx, fn)` (doc 01 §5.3) issues, inside `BEGIN`:

```sql
SELECT set_config('app.account_id',   $1, true),
       set_config('app.workspace_id', $2, true),   -- '' when the route is account-level
       set_config('app.request_id',   $3, true);
```

`true` = transaction-local, so the settings vanish at `COMMIT`/`ROLLBACK` and pooled connections never carry them to another request (doc 01 §9.2). Account-level routes (`/me/*`) set only `app.account_id`.

### 3.3 System operations

The complete list of operations that cross the tenant or account boundary. Each is a `SECURITY DEFINER` function owned by `slugbase_system` with `SET search_path = pg_catalog, public, pg_temp` (`pg_temp` last, so the session's temporary schema, which PostgreSQL otherwise searches first for table and type names, cannot shadow an unqualified name), a narrow signature, no dynamic SQL, `EXECUTE` revoked from `PUBLIC` and granted to `slugbase_app`, and an audit or log line where noted. Every function is listed in the reviewed registry `packages/db/src/system/registry.ts`; `pnpm db:check` fails for a `SECURITY DEFINER` function that is not registered and for a registry entry without a function. Adding one is a risk-flagged change (doc 10). The exception is an **internal operation**, one that only other system operations call and the application never does; the registry marks it (`internalSystemOperations`), and the `system-operations` rule holds it to every other check but requires the opposite grant: neither `PUBLIC` nor `slugbase_app` may execute it, so a ceiling or a guard its callers apply cannot be got round by calling it directly. The callers run as `slugbase_system`, the owner, which needs no grant. `sys_create_workspace` is the one internal operation. A migration creates the function as `slugbase_owner` and hands it to `slugbase_system` as §3.1 describes.

| `sys_session_lookup(token_hash)` | Runs before any account is known | Session + account principal (session id, account id, level, active workspace as stored, `reauth_at`, instance-admin flag) — one round trip per request. The membership role is not part of it: the tenant resolver reads the account's memberships under row-level security, once per request (doc 01 §5.2). A row comes back only for a session that is not past its sliding or absolute expiry, whose account is not disabled and which was not created before the account's `password_changed_at`; a deleted session is gone, so revocation holds on the next request. A full session last seen more than a minute ago has `last_seen_at` and its sliding expiry (30 days, 90 with `remember`, never past `absolute_expires_at`) moved forward in the same call, so there is no separate touch function. It does not filter on `deleting_at`: a workspace being deleted stops being reached because the mark clears the sessions' active workspace and the memberships the resolver reads leave it out (§7.2) |
| `sys_session_create(id, account_id, level, remember, ip_prefix, ua, token_hash, replaced_token_hash)` / `sys_session_rotate(id, account_id, new_token_hash)` / `sys_session_revoke(id, account_id)` / `sys_session_revoke_all(account_id, except_id)` / `sys_list_sessions(account_id, after_id, max_rows)` | Sessions are not readable by the app role | `create` takes the id the application generated (Q91) and, in one call, inserts a session of the level given (`full`, or `partial` with the 5-minute sliding and absolute expiry of doc 02 §2.3, which a lookup does not extend), deletes the session of `replaced_token_hash` when given (the cookie the sign-in request carried, whichever account it belonged to), sets the account's `last_sign_in_at` for a `full` session and answers `false`, changing nothing, for an unknown or disabled account and for a level that does not fit the account's second factor (`partial` only for an account whose MFA is on, `full` only for one whose MFA is off, doc 10 T17); the expiries are set from the database clock; `revoke` deletes one session of the account named and says whether it existed; `revoke_all` deletes every session of the account except `except_id` (all of them when it is null), whatever their level or expiry, and answers how many; `list` returns one page of the account's sessions that are valid now (full, within both expiries, not created before `password_changed_at`, the account not disabled): id, created and last-seen time, coarse IP prefix and user agent, never the token hash; ordered by identifier descending (UUIDv7, so newest first), resuming after `after_id` for at most `max_rows` rows. | `sys_mfa_get_secret(account_id)` / `sys_mfa_set(account_id, action, secret, key_id, expected_secret)` / `sys_mfa_accept_step(account_id, step)` / `sys_backup_codes_replace(account_id, ids, hashes)` / `sys_backup_code_consume(account_id, code_id)` | MFA material is column-protected and `mfa_backup_codes` has no app access | `get_secret` returns the sealed secret, its key id, `enabled_at` and `last_step` of an account that exists, is not disabled and has a secret (pending or active); no row otherwise. `set` is the one writer of the secret and of `mfa_enabled_at`: `start` stores a pending secret (replacing an earlier one, resetting `mfa_last_step`) and refuses an account whose MFA is on; `reseal` stores the same secret under another key only while the stored ciphertext is still `expected_secret`; `activate` sets `mfa_enabled_at` only while MFA is off, the stored ciphertext is `expected_secret` and a step was accepted for it. `sys_mfa_accept_step` atomically rejects a step ≤ `mfa_last_step`, so one code is accepted once. `sys_backup_codes_replace` gives an account whose MFA is on exactly the given set of 1 to 20 codes (application-generated UUIDv7 ids and argon2id hashes), deleting the old set in the same call; `sys_backup_code_consume` marks one unused code of the account as used and says whether it did, so a code presented twice at once is accepted once. Enrolment confirmation runs `accept_step`, `set(activate)`, `backup_codes_replace` and `sys_session_rotate` in one transaction; a failure at any step leaves the pending enrolment, no codes and the old token. The second-factor sign-in adds three: `sys_backup_codes_unused(account_id)` lists the id and argon2id hash of each unused code of an account whose MFA is on (the database cannot verify a salted hash, so the application verifies the typed code against each and consumes the matching one by id); `sys_session_promote(id, account_id, new_token_hash)` turns one live, unexpired `partial` session of an account whose MFA is on into a `full` one under the new token (created now, the sliding window of its `remember` flag, the 180-day cap from now, `mfa_failures` cleared, `last_sign_in_at` set) and answers whether it did; `sys_session_mfa_failure(id, account_id)` counts one refused code against a `partial` session, deletes it at the fifth and answers whether the session is over. The sign-in runs `sys_mfa_accept_step` (a TOTP code) or `sys_backup_code_consume` (a backup code) and then `sys_session_promote` in one transaction, so a failure at either leaves the code unused and the session partial. Managing the factor adds two: `sys_mfa_lock(account_id)` takes the row locks a change of the whole second factor needs, in the one order every writer of these rows uses (the account's backup-code rows by id, then the account row, then the session row) and answers false for an account that does not exist, is disabled or has MFA off; `sys_mfa_disable(account_id)` clears `mfa_secret`, `mfa_secret_key_id`, `mfa_enabled_at` and `mfa_last_step` and deletes every backup code of the account, used ones included, and answers false, changing nothing, when MFA was not on. Regenerating the backup codes runs `sys_mfa_lock`, `sys_mfa_accept_step` and `sys_backup_codes_replace` in one transaction; turning MFA off runs `sys_mfa_lock`, then `sys_mfa_accept_step` or `sys_backup_code_consume`, then `sys_mfa_disable` and `sys_session_rotate`; re-authenticating with a code runs `sys_mfa_accept_step` and `sys_session_reauth`. A sign-in with a backup code locks its code row and then the account row, so the management paths lock the code rows before the account row: taking the account row first (as `sys_mfa_accept_step` does) would let the two wait for each other. A failure at any step of any of them leaves the old codes, the factor on, the old token and the step unspent |
| `sys_account_password_hash(account_id)` | The password hash is column-protected and the application verifies it | The argon2id hash of an account that exists, is not disabled and has a password; NULL for every other case, which callers treat alike |

| `sys_session_set_active_workspace(session_id, account_id, workspace_id)` | `sessions` is not readable or writable by the app role | Sets `active_workspace_id` of one full session of the account, and says whether it did, only when the account is a member of the workspace and the workspace is not being deleted; the membership is checked as of that statement's snapshot and takes no lock on the membership row, so a removal that commits concurrently can leave the session naming the workspace, and the tenant resolver re-derives the active workspace from the account's memberships on the next request. A workspace the account does not belong to, one being deleted, a session of another account, a partial session and an unknown session change nothing and answer false (doc 04 section 10.4) |
| `sys_password_set(account_id, hash)` | Column-protected | Stores a hash that has the shape of an argon2id PHC string (the `$argon2id$` prefix, an optional version field, the `m`, `t` and `p` parameters, and a non-empty base64 salt and hash; any other string, one with leading or trailing whitespace included, is refused) and sets `password_changed_at` to now (invalidates the account's sessions created before it); false, changing nothing, for an unknown or disabled account. It does not check the lengths of the salt or hash or that the hash decodes: the application's hasher is the only writer. The password change runs it, `sys_session_rotate` and `sys_session_revoke_all(account_id, current session)` in one transaction, in that order: the account row is locked first, so two changes made at once queue instead of deadlocking, and a failure at any step leaves the old password, the old sessions and the old token |
| `sys_api_token_lookup(token_hash, ip_prefix)` | Runs before any account is known; `slugbase_app` has no SELECT on `token_hash` | Token principal (token id, account id, bound workspace id, scope) in one round trip, one row at most: a row comes back only for a token that is not revoked and not expired, whose account is not disabled and whose workspace is not being deleted, and a token whose membership ended is already gone (the composite foreign key), so an unknown, revoked, expired, disabled-account and membership-less token are one answer and cause no write. The role is not part of it: the tenant resolver reads the account's membership in the bound workspace for each request (doc 01 §5.2). A token last used more than a minute ago has `last_used_at` (database clock) and `last_used_ip_prefix` (`ip_prefix`, the coarse prefix of the request, null when unknown) written in the same call, conditioned on the same interval in the update, so a concurrent request finds the time fresh and does not write it again; `slugbase_app` cannot write either column |

| `sys_oidc_state_create(state_hash, provider, intent, nonce, code_verifier, key_id, return_to, link_account_id, invitation_token_hash)` / `sys_oidc_state_take(state_hash, provider)` / `sys_identity_sign_in(provider, subject, session_id, ip_prefix, ua, token_hash, replaced_token_hash)` | OIDC callback is anonymous, and `oidc_login_states` has no app access | `create` stores the handshake for 10 minutes on the database clock (the intents `login`, `link`, `reauth` and `invite`; `invite` requires a 32-byte `invitation_token_hash` and no link account, and every other intent requires none) and refuses a return path that is not relative; `take` deletes the record and returns it, with its `invitation_token_hash`, in one statement, so a state is answered once, and returns nothing for an unknown, expired, already consumed or other-provider state; it is what the callback uses. `sys_identity_sign_in` finds the account an identity is linked to and, in one call, inserts a `full` session (30-day sliding window, 180-day cap), deletes the session of `replaced_token_hash` when given, and sets the account's `last_sign_in_at` and the identity's `last_used_at`; it answers `false`, changing nothing, for an identity nobody linked and for a disabled account. The session is `full` whether or not the account's MFA is on: a successful OIDC sign-in never asks for SlugBase TOTP (doc 02 §2.3), the one case where a `full` session is created for an account with MFA on. A first login, for an identity nobody linked, that the provider asserted with a verified address runs in one transaction. It tries `sys_identity_sign_in` first, and a linked identity signs in with nothing else written. Otherwise `sys_identity_link_by_email` links the identity to the enabled account that holds the address verified, and `sys_identity_sign_in` then creates the session. When no such account exists and the provider allows creating one, the transaction runs `sys_create_account` (the address verified, no password), `sys_identity_link` to the new account, the personal workspace (provisioned only when public registration is on; with it off the account has none), the `account.created` job (queued in the transaction, so it exists only if the account does) and `sys_identity_sign_in`, in that order. A refusal at any step writes nothing: `taken`, a provider that does not allow creating an account, a `sys_create_account` that answers `false` (the address is held by an account that never verified it or by a disabled one, or is reserved by an undo link, so no second account is made for it), a link that does not answer `linked` or a sign-in that answers `false` after the link all roll back whatever the transaction wrote (account, identity, workspace, job, session). A sign-in that answers `false` for an account the transaction just created is an error, not a refusal, and rolls back the same way |

The match is case-insensitive (`accounts.email` is `citext`) and the caller passes the address trimmed and NFKC-normalised; the lookup locks the matching row, so the match is judged on the row as it stands when the identity is written. ## 4. The `/go` resolution query

Goal: resolve `slug` for `(workspace W, account A)` among bookmarks A can access that have forwarding on and aren't archived — in one round trip, from indexes only.

**Candidate-then-filter.** The number of bookmarks in one workspace carrying the same slug is tiny (at most one per member), so the query first fetches all candidates by `(workspace_id, slug)` from `bookmarks_slug_idx` (index-only thanks to `INCLUDE`), then filters them by access with `EXISTS` probes that each hit a narrow index:

```sql
WITH candidates AS (
  SELECT id, owner_id, url
  FROM bookmarks
  WHERE workspace_id = $W AND slug = $slug AND forwarding AND plan_archived_at IS NULL
), my_teams AS (
  SELECT team_id FROM team_members WHERE workspace_id = $W AND account_id = $A
)
SELECT c.id, c.url, c.owner_id,
       (SELECT bookmark_id FROM slug_preferences
         WHERE workspace_id = $W AND account_id = $A AND slug = $slug) AS preferred_id
FROM candidates c
WHERE c.owner_id = $A
   OR EXISTS (SELECT 1 FROM bookmark_shares s WHERE s.workspace_id = $W AND s.bookmark_id = c.id
                AND (s.target_account_id = $A OR s.target_team_id IN (SELECT team_id FROM my_teams)))
   OR EXISTS (SELECT 1 FROM folder_bookmarks fb JOIN folder_shares fs
                ON fs.workspace_id = fb.workspace_id AND fs.folder_id = fb.folder_id
              WHERE fb.workspace_id = $W AND fb.bookmark_id = c.id
                AND (fs.target_account_id = $A OR fs.target_team_id IN (SELECT team_id FROM my_teams)));
```

RLS adds `workspace_id = app_workspace_id()` to every table reference; it matches the explicit predicate, so the planner keeps the same index paths **for a predicate whose operator is leakproof**. In the plans measured for this query on PostgreSQL 17.11 and 18.6, a condition of the query on a table with a policy is an index condition only when its operator is leakproof; otherwise it is a filter over everything the index returns for the workspace. `texteq` and `uuid_eq` are leakproof, `citext_eq` is not (`pg_proc.proleakproof`, read on 18.6). Measured on a seeded 50 000-bookmark workspace (`pnpm perf:go`, doc 12 §5; 18.6, one request at a time through PgBouncer): with `slug citext` the plan is still an `Index Only Scan` on `bookmarks_slug_idx` with no sequential scan, but its index condition is only `workspace_id` and 45 255 index entries are removed by the slug filter. That filter takes about 9.6 ms of execution at p50 (against 0.05 ms with the slug in the index condition) and grows with the workspace (0.94 ms at 5 000 bookmarks, 3.7 ms at 20 000). The plan's estimated cost, 1.9 to 2.6 million, is also far above PostgreSQL's `jit_above_cost` (100 000), so with the default `jit = on` every request is JIT-compiled: execution p50 152 ms, of which 142 ms is compilation, and a client-observed p95 of 181 ms (14.9 ms with `jit = off`; 2.5 ms with RLS off). With `slug text` the slug is in the index condition, the plan costs about 45, nothing is compiled, and the p95 is 2.5 ms with `jit` on or off. The column the candidate lookup compares therefore needs a leakproof equality, which `slug citext` in §2.4 and §2.6 does not have; the amendment to `text` (lower-case by the grammar and by the application) is a follow-up item (#373, doc 12 §5). Setting `jit = off` for the application role removes the compilation and not the filter.

The integration suite asserts with `EXPLAIN (FORMAT JSON)` on a seeded 50 000-bookmark workspace that the candidate scan is an `Index Only Scan` on `bookmarks_slug_idx` **whose index condition contains `slug`** (not only `workspace_id`), and that no sequential scan appears (doc 08 §4). An `Index Only Scan` alone proves nothing: the slow plan above is one. The guard against sequential scans stays for the share, folder and team tables too, and it depends on the fixture. In the spike's fixture the planner read `bookmark_shares` sequentially for a slug with dozens of candidates, and the scan read the whole table (283 rows kept, 6 716 removed by its filter; 0.6 ms): the table held 6 999 rows across 2 000 workspaces, 5 000 of them (71 %) in the one large workspace. That scan is cheap only because one workspace dominates the table, and on a table of many workspaces it is a read of every tenant's rows, which is what the guard exists to catch. The suite's fixture therefore has to spread the share, folder and team rows over many workspaces so that no workspace dominates them; whether the planner then keeps the index paths on those tables was not measured, because the spike's fixture is dominated by the large workspace by design.

The same access predicate, as a reusable SQL fragment in the repository, backs `scope=shared_with_me` lists, `GET /bookmarks/{id}` for non-owners, search, and `GET /go/suggest` (where the candidate set is `slug LIKE prefix || '%'` on `bookmarks_slug_idx`, capped at 50 candidates before filtering). When the query returns no candidate, `POST /go/resolve` calls `sys_go_other_workspaces` (§3.3) so the not-found page can offer the member's other workspaces; that lookup never runs for a hit and never forwards across workspaces.

## 5. Migrations

### 5.1 Generation and review

- The schema lives in `packages/db/src/schema/*.ts` (Drizzle). `pnpm db:generate` runs drizzle-kit and writes `packages/db/migrations/<timestamp>_<name>.sql` plus its snapshot. Names: `add_<thing>`, `index_<thing>`, `drop_<thing>`.
- **RLS policies, grants, functions, triggers and extensions are not expressible in the Drizzle schema** as needed, so they live in `packages/db/src/sql/*.sql` — declarative, idempotent definitions (`CREATE OR REPLACE FUNCTION`, `DROP POLICY IF EXISTS … ; CREATE POLICY …`, `GRANT …`). drizzle-kit is configured to emit them as a **custom migration step** appended to the generated migration whenever those files change (`pnpm db:generate` diffs them against the last applied hash). They are reviewed exactly like generated DDL (Q51).
- A migration file is committed only as the generator's output and **never edited after it is merged to `dev`**. CI verifies: regenerating from the schema produces no new migration (no drift); every committed migration's checksum matches its recorded checksum; the custom-SQL hashes match.
- `drizzle-kit push` is never used anywhere — not locally, not in CI.

### 5.2 Expand / contract

Several server replicas run during a rolling deploy, so every migration must be compatible with the code version **before and after** it:

1. **Expand** (release N): add nullable columns, new tables, new indexes `CONCURRENTLY` (drizzle-kit's generated `CREATE INDEX` is rewritten by the generator wrapper to `CONCURRENTLY` for existing tables, each build in a non-transactional migration of its own), new enum values. Code N writes both old and new shapes where needed.
2. **Backfill** (a pg-boss job in release N, batched, idempotent, resumable) — never inside the migration transaction for tables that can be large.
3. **Contract** (release N+1 or later, after N is fully deployed): add `NOT NULL`/constraints `NOT VALID` then `VALIDATE CONSTRAINT`, drop old columns.

CI's migration check rejects in a single migration: dropping or renaming a column or table that existed in the previous release, adding a `NOT NULL` column without default, adding a column that rewrites an existing table under an `ACCESS EXCLUSIVE` lock (a serial type, an identity column, or a generated column not marked `VIRTUAL`, since PostgreSQL 17 has stored ones only; a nullable column or one with a constant or stable `DEFAULT`, such as `now()`, does not rewrite, unless its type is a domain with a `CHECK` or `NOT NULL` constraint, which validates every existing row and which the check also rejects: it reads the domains from every `CREATE DOMAIN` of the migration chain, accepts built-in and array types, enums and domains without constraints, and rejects a type name it cannot show to be one of those; it also rejects a column of a domain whose default, from `CREATE DOMAIN … DEFAULT` or a later `ALTER DOMAIN … SET DEFAULT`, is not a constant or a call it accepts as stable, such as `random()`, because every existing row then takes its own value and the table is rewritten, unless the column states a default of its own; a domain with a constant default, one whose default was dropped, and an array of the domain are accepted, and a domain over a domain takes its base's default when it is created), adding `NOT NULL` to a column of an existing table (`SET NOT NULL` or a `NOT NULL` table constraint), dropping the default of one (`DROP DEFAULT` or `SET DEFAULT NULL`), type changes that rewrite a table, non-concurrent index creation on an existing table (which includes adding a `PRIMARY KEY`, `UNIQUE` or `EXCLUDE` constraint, also as the inline constraint of an added column, and attaching an existing index as the primary key with `PRIMARY KEY USING INDEX`; only `UNIQUE USING INDEX` attaches an index without being rejected), adding a `CHECK` or `FOREIGN KEY` constraint to an existing table without `NOT VALID` (including an inline `CHECK` on an added column and an inline `REFERENCES` on an added column that has a default) — unless the file is the contract half of an expand/contract pair (below) and the dropped object has been unused for at least one release (Q52). The statements that add a system operation (§3.3) are accepted in a migration without a contract header, and nothing broader: `CREATE FUNCTION` in any language, with or without `SECURITY DEFINER`, and `CREATE OR REPLACE FUNCTION` of a function the migration chain declares with the same argument types and return type, or of one the chain does not declare (provided the check read every earlier statement), whose body is a string that is not analysed as migration statements; `ALTER FUNCTION … OWNER TO slugbase_system` and `REVOKE ALL ON FUNCTION … FROM PUBLIC` for a function the same file creates; `GRANT EXECUTE ON FUNCTION … TO slugbase_app`; and `GRANT CREATE ON SCHEMA … TO slugbase_system` with the `REVOKE CREATE ON SCHEMA … FROM slugbase_system` that takes it back in the same file, with only `CREATE FUNCTION` and `ALTER FUNCTION … OWNER TO` statements between the two. It rejects, unless the file is the contract half of a pair, a replacement that changes a function's return type or that it cannot show is a new function, `DROP FUNCTION`, any other owner or action of `ALTER FUNCTION`, a schema `CREATE` grant to another role or one the file does not revoke, a statement other than those two between the grant and the revoke, and `GRANT EXECUTE` to `PUBLIC` or to any role other than `slugbase_app`; a function named like a built-in the check lets a migration call is not accepted, and the tenant context functions stay one `LANGUAGE sql` `SELECT` of built-ins. Because a function body runs when a statement calls the function, which a default, a policy or an index expression can do, also without a parenthesis (`(t).f` is `f(t)` for a row type `t`), the check rejects any statement outside those function statements and the trigger form below that mentions the name of a function the chain declares (as a word or a quoted identifier, compared on the text as written, as PostgreSQL compares names: only the letters A to Z folded to lower case, with no Unicode case mapping, a quoted name read as the unquoted one, and both cut to 63 bytes at a character boundary; qualified or not; a column named like it is rejected too). It does not read a `CREATE FUNCTION` whose name, quoted or not, has a character outside printable ASCII (so every function name the check holds is ASCII), nor one named with more than 63 bytes, which PostgreSQL stores under a shorter name, nor one that can be called with a single argument of a type that is not a built-in (a first input argument of such a type whose later input arguments all have a default, or a `VARIADIC` one), since field-selection notation can call it. The trigger forms it reads are `CREATE [OR REPLACE] TRIGGER <name> BEFORE UPDATE ON <table> FOR EACH ROW EXECUTE FUNCTION <function>()` and `CREATE CONSTRAINT TRIGGER <name> AFTER DELETE OR UPDATE ON <table> DEFERRABLE INITIALLY DEFERRED FOR EACH ROW EXECUTE FUNCTION <function>()`, with no column list, `WHEN` condition, argument, other timing or event, and no other constraint trigger or event trigger (PostgreSQL has no `CREATE OR REPLACE CONSTRAINT TRIGGER`); each is accepted only when the function is one an earlier statement of the chain declares without arguments as `RETURNS trigger`, because a trigger function runs on a row write (or, for the deferred form, at the commit of the transaction that wrote it), which a migration does not make, and not when the trigger is created. A constraint trigger is made again by dropping it first, and `DROP TRIGGER [IF EXISTS] <name> ON <table>` (no `CASCADE` or `RESTRICT`) is accepted only when the same file creates the trigger of that name and table again with the function and the form it had (a plain `BEFORE UPDATE` row trigger stays one, a deferred `AFTER DELETE OR UPDATE` constraint trigger stays one; `CREATE OR REPLACE TRIGGER` over a trigger the chain created is held to the same); a trigger of the release that is dropped and not created again, or created again with another function or the other form, is rejected, as is a drop after a statement the check cannot read, which may have changed the trigger. It also rejects every data-changing statement, `INSERT` (also `INSERT … SELECT`), `UPDATE`, `DELETE`, `TRUNCATE`, `MERGE` and `COPY … FROM`, whether it stands alone or sits in a CTE or in the query of a `CREATE TABLE … AS`; the contract header never licenses one, and none is allowed on a table the migration creates, because migrations stay schema-only and a backfill is a worker job (step 2, D25). `lock_timeout = '5s'` and `statement_timeout = '15min'` are set for every migration session; a migration that can't take its lock fails rather than queueing traffic behind it. A non-transactional `CONCURRENTLY` step runs with `lock_timeout` off and `statement_timeout` as its bound: its lock queues no application traffic, and the build waits for transactions that could write to its table (holding a lock that conflicts with its SHARE lock, such as an uncommitted INSERT, UPDATE or DELETE) and, after its second scan, for every transaction in the same database whose snapshot predates that scan, whatever table it reads. `migrate` sets `client_connection_check_interval` (1 s), which needs a PostgreSQL server that supports it (a server on Windows rejects it, and `migrate` then fails while setting up its session, before it takes the lock or applies anything). A build whose client closes its connection, a killed `migrate` or a stopped container, is then cancelled by PostgreSQL instead of finishing unrecorded. A client host that vanishes without closing its connection (power loss, a network partition) sends the server no FIN or RST, so `migrate` also sets `tcp_keepalives_idle` (60 s), `tcp_keepalives_interval` (10 s) and `tcp_keepalives_count` (6) for its session: the server then reports such a connection closed after about two minutes, a small fraction of `statement_timeout`, and the connection check cancels the build. These settings apply to a TCP connection; over a Unix-domain socket the peer is on the same host and cannot vanish alone. Because each build is its own migration, a failed build (the `statement_timeout`, a duplicate in a unique index, a cancelled client) leaves at most its own INVALID index and no record; the next run drops that index and rebuilds it, with no manual step. A valid index of the same name is never dropped. One window remains, which can leave a valid index with no record, which the operator drops: a crash between the end of a build and the insert of its bookkeeping row (milliseconds).

**Re-emitted custom SQL.** The check also rejects a `REVOKE` on a table the previous release holds, since a running replica may lose the access it uses. Every migration that changes `src/sql/` carries all of it again as a custom step (§5.1), so the `REVOKE … ON TABLE` statements of the release come back in each later step. What a `REVOKE` does depends on the `GRANT`s on the same table around it, so a `REVOKE` on named tables is accepted, without a contract header, only when it stands in the migration's own custom step (the statements from the `-- slugbase:custom-sql` marker to the end of the file) and, for each table it names, the `GRANT` and `REVOKE` statements on that table in that step, with those on a wider object (a schema, `ALL TABLES IN SCHEMA`), are the same and in the same order as in the latest custom step of the previous release (read from git at its tag): the step then leaves the table the privileges the release left it. The statements are compared with comments removed and runs of whitespace collapsed to one space; letter case, privileges, roles, the order of tables and the quoting of names stay as written. A `REVOKE` outside the custom step, or on a table whose `GRANT`s or `REVOKE`s differ from the release's (a `GRANT` dropped, moved before the `REVOKE`, or added), changes what the table allows and is rejected as above. A `REVOKE` on a schema, a sequence, a database or `ALL TABLES IN SCHEMA` is not accepted this way, nor is any other statement a re-emit repeats: each is judged on its own. Where the release has no custom step, or either step holds a `GRANT` or `REVOKE` the check does not read, no statement counts as already applied.

**Tables created by custom SQL.** "A table the previous release holds" is read from git at the release tag: the tables of the Drizzle snapshot of its last migration, and the tables its custom SQL creates, which the snapshot cannot hold (the `UNLOGGED` table of `040-rate-limit.sql`, say). The latter are every `CREATE [UNLOGGED] TABLE [IF NOT EXISTS]` of the latest custom step of the release, with the columns of its list and those that `ALTER TABLE … ADD`, `DROP` or `RENAME COLUMN` statements of the same step add, remove or rename; the latest step is the one that re-emits all of `src/sql/`. Every rule above then judges such a table as a table of the schema, and a re-emitted `REVOKE` on it is accepted under the conditions of the previous paragraph. Re-emitting the `CREATE TABLE IF NOT EXISTS` of such a table is accepted as long as its column list is the one the release created the table with (compared with comments and layout left out): the statement leaves an existing table as it is, so another list would never reach a database that has the table, and the check reports it; a column is added or dropped with `ALTER TABLE`, which the rules above judge. A custom step that creates a table whose columns the check cannot name (a `LIKE` clause, `CREATE TABLE … AS`) makes the check fail. Views, sequences and other objects that custom SQL creates are not part of the release state.

**Re-emitted function statements.** A contract migration that drops a function keeps its `DROP FUNCTION IF EXISTS` in a `src/sql/` file, and one that takes a role's access to a function away keeps its `REVOKE … ON FUNCTION … FROM <role>` there, so every later custom step carries the statement again. The check reads `DROP FUNCTION [IF EXISTS] f(args)` of one function with an argument list, and a `REVOKE` on one function, each without `CASCADE` and with a name of printable ASCII within 63 bytes; any other `DROP FUNCTION` or function `REVOKE` stays a statement it cannot place. A statement of that shape is accepted without a contract header only when it stands in the migration's own custom step and an earlier migration of the journal (shipped in a release or added since) ran the identical statement in its custom step while carrying a valid contract header (compared as above: comments removed, whitespace runs collapsed, the rest as written). A migration without a valid header licenses nothing, and a drop or `REVOKE` that no earlier migration with a valid header ran needs the header. Why it is safe: the earlier migration ran the statement behind the expand/contract pair (Q52) for every database that reached it, so the re-emit repeats an effect that is already there, and `DROP FUNCTION IF EXISTS` finds nothing to drop. The licence ends where the chain may have undone the statement: after a migration or statement the check cannot read, and, for a drop, after a `CREATE FUNCTION` of a function with the same schema, name and number of arguments (the nine-argument `sys_oidc_state_create` beside the dropped eight-argument one does not end it). A re-emitted `REVOKE` also needs the custom step to leave the function the `GRANT` and `REVOKE` statements on it, and on any wider object, that the latest custom step before it left it, in the same order, so a `GRANT` added to `src/sql/` is not undone unseen. A drop without `CASCADE` fails while a trigger, a default, an index or a policy depends on the function, so neither statement creates, replaces or removes a trigger or changes a type; the statements after it are judged on their own, as they would be without it.

**Writing and landing a contract migration.** A step the check rejects is accepted only with a **contract header** in the leading comment block of the migration file, exactly one line: `-- slugbase:contract expand=<migration tag> release=<version>`. `<migration tag>` is a migration of the journal (for example `20260301000000_add_name`), and `<version>` is a release tag of this repository, written `MAJOR.MINOR.PATCH` with an optional pre-release suffix and an optional leading `v` (`1.2.0`, `v1.2.0`, `1.2.0-rc.1`). The named release must already contain the expand migration, so the expand step has shipped in a release before the one that carries the contract file (Q52). No header, a second header, a malformed one, an unknown migration or release, or an expand migration the release does not contain is rejected. The header alone decides, on every event: `pnpm db:check` takes no argument or environment value that changes its verdict, and no pull-request label takes part.

`pnpm db:generate` writes the header, so the checksum recorded by `pnpm db:record-checksums` covers it from the start and the file is never edited after generation (§5.1): `pnpm db:generate --name drop_<thing> --contract expand=<migration tag> release=<version>`. The generator refuses a malformed value, an expand migration that is not in the journal, and a run that writes no file able to hold a contract step (an index build alone), and in each case writes nothing. Whether the release exists and contains the expand migration is read from git by `pnpm db:check`, which also needs the release tags: it fails in a shallow clone, where the history and tags are not there, so CI checks out the full history and every tag, and a local clone runs `git fetch --unshallow --tags` first. A repository with no release tag has nothing to compare with, and every object then counts as unreleased.

A contract migration lands on `dev` by cherry-pick and reaches `main` in the promotion pull request from `dev`. Its `pnpm db:check` run passes on a push and on a pull request alike, because the valid header is the whole condition. The maintainer approves the step by merging the promotion pull request, which is the review of the destructive change; the check proves only that the expand migration shipped first. A data-changing statement and a `lock_timeout` or `statement_timeout` setting are rejected on every event, with or without a header.

### 5.3 Applying

- `migrate` takes the advisory lock `hashtext('slugbase.migrate')` by polling `pg_try_advisory_lock`, so a waiting `migrate` holds no snapshot that a concurrent index build would wait on. It applies pending migrations chain by chain (§5.5), each migration in its own transaction (or non-transactional for `CONCURRENTLY` steps), records it, releases the lock. A second concurrent `migrate` waits, then finds nothing to do.
- **CE image:** the entrypoint runs `migrate` with `DATABASE_MIGRATE_URL` first (a failure exits non-zero before anything serves), then starts the server with `DATABASE_MIGRATE_URL` removed from its environment and in-process migration disabled; the worker never receives the migrator URL. Several CE replicas starting at once are safe: one migrates, the others wait on the lock.
- **In-process variant** (`MIGRATE_ON_START=true` without the entrypoint: development, bare `node` runs and the single-container mode of Q11): the server runs the same migration under the same lock before serving application routes, using `DATABASE_MIGRATE_URL`. The probes answer at once, `/ready` stays 503 and every other route returns `503 unavailable` until it finishes.
- **Managed deployments (D25):** with `MIGRATE_ON_START=false` the server never migrates; a deployment may then run the `migrate` command of the **new** image as a separate one-shot step **before** rolling out the new server and worker containers, and roll out only after it exits 0, so the migrator URL is held only by that step (D24; Cloud doc 07 §5.5).
- A server whose build expects a migration level **higher** than the database refuses readiness; one that finds the database **ahead** of it (a newer migration it doesn't know) logs a warning and keeps serving — expand/contract guarantees N−1 code works on N's schema.

### 5.4 Enums and reference data

Adding an enum value is expand-only; removing one is a contract migration after no row uses it. Reference data (plan catalog, accent palette, the folder icon allowlist) is **configuration in code**, not table rows — no data migrations for it.

### 5.5 The cross-repository chain

| Order | Chain | Bookkeeping | May reference |
|---|---|---|---|
| 1 | CE `public` | `drizzle.migrations_core` | itself |
| 2 | pg-boss | its own version table; `drizzle.pgboss_pending_builds` while an upgrade's index builds are still owed (owner-only, no grant to `slugbase_app`) | — |
| 3 | Cloud `cloud` | `drizzle.migrations_cloud` | `public` |
| 4 | Cloud `console` | `drizzle.migrations_console` | `public` (views only) |

- **FK direction is one-way:** Cloud tables may reference `public` tables (e.g. a `cloud` table keyed by `workspace_id → public.workspaces ON DELETE CASCADE`); `public` never references `cloud` or `console`. Billing data has no foreign keys into SlugBase at all: it lives in the external billing service and is linked only by the workspace id (D29). CE therefore builds, migrates and runs with no knowledge of them.
- A CE contract migration that drops or changes a column Cloud references, or that Cloud's `console_mirror` views read, is a **cross-repo contract change**: the CE item names it, and the Cloud follow-up lands before the CE contract step is released (doc 09 §3).
- **The pg-boss chain** is run by `migrate` as `slugbase_owner`, under the `migrate` advisory lock: it installs the schema when the database has none, upgrades an older one to the version this build runs with pg-boss's own migration plan, and refuses a newer one (or one older than pg-boss can upgrade from). The plan's transaction runs as one statement; the concurrent index builds it appends run one at a time outside a transaction, with `lock_timeout` off and `statement_timeout` as their bound (§5.2). pg-boss stamps the new version before those builds, so they are first recorded in `drizzle.pgboss_pending_builds`, which `slugbase_app` has no grant on; a later `migrate` run under the lock finishes what the record still owes. The worker never installs or upgrades the schema.
- Cloud's `migrate` applies CE's chain from the submodule-pinned CE commit, so Cloud never runs an unreleased CE migration by accident.

## 7. Deletion and data subject requests

### 7.1 Account deletion (`DELETE /me`, `sys_delete_account`)

In one transaction:

1. Refused with `422 validation_failed` and the field code `last_instance_admin` if the account holds `is_instance_admin` and no other enabled account does (doc 02 §6; an admin who is disabled does not count as another one, as in `sys_instance_update_account`). The decision is taken by `sys_account_last_instance_admin` under a transaction-level advisory lock that serialises the instance admins' deletions, after the locks on the account's workspaces and on its row and before the deletion guard is asked, and `sys_delete_account` takes it again, so two admins deleting themselves at once leave one. A path that clears the flag of an instance admin or deletes an account that holds it (the instance routes) takes the same advisory key, `slugbase.instance_admins`, after the rows it locks; without it that path and a deletion each read the other admin as still there. `sys_instance_delete_account` does, for an account that holds the flag, and answers `last_instance_admin` before it deletes. `sys_instance_update_account` does: under the key it re-reads the other admins in a statement of their own and count only those that are not disabled, and it refuses with `last_instance_admin` when none remains. Refused with `409 last_owner` if the account is the **only owner** of any workspace that has other members — the owner must transfer ownership or delete that workspace first; the problem body lists the blocking workspaces by id and name. Refused with `409 billing_active` on Cloud while it owns a workspace with an active paid subscription. The rows are locked in one order by `DELETE /me` and by the instance route (`sys_account_deletion_scope`, `sys_instance_account_deletion_scope`): the account's workspaces that are not being deleted in identifier order, then its `mfa_backup_codes` rows in identifier order (the order of `sys_mfa_lock`, since the deletion cascades to them, so a deletion waits behind a backup-code sign-in, a regeneration, a disable of the second factor, an administrator's reset or the redemption of a verification link instead of deadlocking with it), then the account row (for the instance route, the rows of the admin and of the account together in identifier order), then the advisory key.
2. Workspaces where the account is the **only member** are deleted entirely (with all content) through the workspace deletion path (§7.2).
3. In shared workspaces: memberships are removed; the account's bookmarks and folders **stay with the workspace** with `owner_id = NULL` (shown as "Former member"; workspace admins can reassign or delete them — doc 02 §3.5); its tags, tag associations, slug preferences, AI cache, API tokens and team memberships are deleted (cascade).
4. Sessions, identities, credential tokens, backup codes, idempotency keys are deleted; the `accounts` row is deleted.
5. Audit events keep `actor_label` but lose `actor_account_id` (SET NULL); `ip_prefix` of that actor's events is nulled. Events that name the account as their target lose that too: `entity_id` is set to NULL where it names the account and the `transferTo` field is removed from `metadata` where it does, so no audit row holds the account's identifier but one: the instance event `instance.account_deleted` that an instance admin's deletion writes after this clean-up, whose `entity_id` is the identifier of the account it deleted until the retention purge deletes the event (§6; the admin's record of what they deleted; the identifier names no row, and the event holds no address, name or other field of the account). The events that named the account before keep their type and label. `transferTo` is the only field of the audit catalog that holds an account identifier.

Keeping the deleted account's bookmarks and folders as ownerless workspace content is decided (Q54): the workspace's other members rely on them. Personal data about the account (name, email, sessions, tags, preferences) is erased.

### 7.2 Workspace deletion

`DELETE /workspace` (owner, re-auth) or instance-admin deletion records the request as an audit event, sets `workspaces.deleting_at` and enqueues the `workspace.delete` job; the request returns `202`. From that moment the workspace is hidden from switchers and APIs, and no member or bound token can read its rows (Q55). The `workspaces` SELECT policy, `app_member_workspace_ids()` and `sys_api_token_lookup` exclude it. `sys_session_lookup` does not: it returns the session's stored active workspace, and a session stops reaching the workspace in three ways. `sys_workspace_mark_deleting` sets `active_workspace_id` to NULL on every session that had it active; `sys_session_set_active_workspace` refuses to point a session at it; and the tenant resolver (doc 01 §5.2) re-derives the request's workspace from the account's memberships, which leave out a workspace being deleted (the membership list filters on `deleting_at` and reads `workspaces` under the SELECT policy above), so even a stored value that still named it would not be used. Cloud refuses the request while a paid subscription is active (cancel first).

The request is one transaction: `sys_workspace_mark_deleting` (§3.3) sets `deleting_at`, points the sessions that had the workspace active at none and revokes the bound tokens, the `workspace.delete` job is queued with the workspace's identifier as its only payload, and `workspace.deletion_requested` is written to the workspace's audit log. The deletion guard (doc 01 §13.2) is asked first, and a refusal or a failure leaves none of it.

The job is idempotent and resumable: it deletes each tenant table's rows in batches (1 000 rows, each batch a transaction of its own, `sys_workspace_purge_batch`) in dependency order, then the workspace row (`sys_workspace_delete_finish`), which cascades whatever is left. A run that stopped halfway is run again from the first table, finds the finished ones empty and continues; a run after the workspace is gone deletes nothing and announces nothing. It touches only the workspace its payload names and only while `deleting_at` is set. The deletion of the members is not held up by the owner rule of §2.2, because the workspace is being deleted. The order is a registry in `packages/db` (`purge-registry.ts`: `api_tokens`, `audit_events`, `bookmark_tags`, `bookmarks`, `tags`, `workspace_invitations`, `workspace_settings`, `workspace_members`), and `pnpm db:check` fails (rule `purge-registry`) when a table with a `workspace_id` column is missing from it, when an entry names no such table, and when `sys_workspace_purge_batch` has no statement for an entry. `workspace.deleted` (payload: `workspaceId`) is emitted as a domain event in the transaction that deletes the row, so once and only when the row is gone.

### 7.3 Access and portability

`GET /export/json` is the member's portable copy of their own content (doc 04 §10.9). A full data-subject access response (account row, memberships, sessions, audit events about them) is produced by the operator: CE instance admin via `/instance/accounts/{id}` + export; Cloud via a console runbook (doc 07 §6).

### 7.4 Backups

Deleted data persists in backups until they age out (Cloud: 30 days of PITR, doc 07 §5). Restores replay deletions recorded since the backup from the audit stream where needed; the privacy policy states the retention (doc 11).

## 8. Seed and fixture data

No seed data ships in migrations.
