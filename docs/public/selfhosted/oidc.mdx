## What you'll accomplish

After this guide, you can add an OIDC identity provider so members can sign in with your organization's SSO instead of (or in addition to) email and password.

## Prerequisites

- Signed in as a workspace **owner** or **admin**
- OIDC provider details: issuer URL, client ID, client secret, and requested scopes
- **Settings → Workspace → Identity providers** visible in the UI (not operator-managed)

## Add an identity provider

<Steps>
  <Step title="Open Identity providers">
    Go to **Settings → Workspace → Identity providers**.
  </Step>
  <Step title="Add provider">
    Click **Add provider** and enter a **Provider name**, **Issuer URL**, **Client ID**, **Client secret**, and **Scopes** (for example `openid email profile`).
  </Step>
  <Step title="Register the callback URL">
    Copy the **Callback URL** shown in the form. Register this exact URL in your identity provider's application settings. Replace `{providerId}` with the provider's id after creation if the placeholder is shown.
  </Step>
  <Step title="Save the provider">
    Click **Add provider**. The provider appears in the list.
  </Step>
  <Step title="Enable sign-in">
    Use **Enable** on the provider row to allow federated sign-in.
  </Step>
</Steps>

Client secrets are stored encrypted at rest and are never logged or exposed in the UI after saving.

## Sign-in experience

After a provider is enabled, the sign-in page offers federated sign-in alongside email and password. Users who authenticate via OIDC can still add a password later from **Account → Password** if they want direct sign-in as well.

MFA applies to password logins only — federated sign-in does not prompt for an authenticator code.

## Manage providers

| Action | Effect |
|--------|--------|
| **Disable** | Stops new federated sign-ins; existing accounts remain linked |
| **Remove** | Deletes the provider configuration |

## Operator-managed identity

If your deployment sets `VITE_OIDC_ADMIN_UI=false`, workspace admins see **Identity providers managed by operator** instead of editable fields. Providers are supplied via deployment configuration on that setup.

## Verify it worked

Open a private browser window, navigate to your instance sign-in page, and complete federated sign-in with a test account. The user should land in the workspace they were invited to.

## Troubleshooting

| Symptom | What to do |
|---------|------------|
| Redirect error from provider | Confirm the callback URL matches exactly, including HTTPS and path |
| Invalid issuer | Verify the issuer URL and that discovery endpoints are reachable from the server |
| User not placed in workspace | Federated sign-in creates or links an account; admins must still invite users into workspaces on invite-only instances |
